## 1. 背景と目的

### 1.1 背景【解釈】

- オブジェクト指向の重要概念（カプセル化、ポリモーフィズムなど）は、用語や定義を読んでも「なぜ必要か」「いつ使うべきか」が実感しにくい。
- 概念のメリットは主に「仕様変更が起きたとき」に現れる。しかし書籍の静的なサンプルコードでは、その変化を体験しにくい。

### 1.2 目的【原文を整理】

オブジェクト設計の重要概念について、**GUIの簡単な操作**で、目的・メリット／デメリット・使い時・ソースコードの変化が分かるWebアプリを提供する。理解度は**コード実装**と**択一クイズ**で確認できるようにする。

## 5. 要求分析（要求から読み取れる課題・リスク）

### 5.1 言語ごとの表現力の差【解釈】— 重要度: 高

必須の3言語は、オブジェクト指向の機能が大きく異なる。

| 機能 | Java | C++ | VBA |
| --- | --- | --- | --- |
| クラス | ○ | ○ | ○（クラスモジュール） |
| アクセス修飾子 | ○ private / protected / public など | ○ private / protected / public | △ Public / Private / Friend のみ（protected なし） |
| 実装継承 | ○ 単一継承 | ○ 多重継承も可 | **× なし** |
| インタフェース | ○ `interface` | △ 純粋仮想関数だけを持つ抽象クラスで代用 | ○ `Implements`（構文が独特） |
| 抽象クラス | ○ | ○ | **× なし** |
| ポリモーフィズム | ○ | ○（`virtual` とポインタ／参照が必要） | △ `Implements` または遅延バインディング（`Object` 型）経由 |
| 引数付きコンストラクタ | ○ | ○ | **×**（`Class_Initialize` は引数を取れない。ファクトリ関数で代用） |
| オーバーロード | ○ | ○ | **×** |
| 例外 | ○ | ○ | △ `Err.Raise` ／ `On Error` |

**ここから分かること**

- 同じ概念でも、言語によって「適切な設計」のコードの形が変わる。たとえば VBA で継承を学ぶ場合は、「継承は使えないので委譲と `Implements` で代用する」という別のコードになる。
- そのため、言語間でコードを自動変換して教材を作るのは難しく、**言語ごとに個別の教材コードが必要**になる。
- 「この言語ではこの概念を直接表現できない」ことを、学習者にどう見せるかを決める必要がある。

### 5.2 コード実装による理解度チェックの判定方法【解釈】— 重要度: 高（最大の技術リスク）

- Java と C++ は、サーバ上の隔離環境（サンドボックス）でコンパイル・実行し、テストで自動採点することが技術的には可能。ただし、学習者が書いた任意のコードを実行するため、隔離の仕組み・サーバ費用・セキュリティ対策の負担が大きい。
- **VBA は実行に Microsoft Office が必要**で、Webサーバ上で安全に実行する一般的な手段がない（Microsoft もサーバ上での Office 自動化を推奨していない）。そのため、VBA は実行による自動採点が事実上できない。
- 「好きな言語」に必須3言語以外も含める場合、言語ごとに実行環境が要る。
- **そもそも、オブジェクト指向の理解はテストの合否では測りにくい。** 不適切な設計のコードでもテストは通るため、実行して採点しても「設計の良し悪し」は判定できない。

→ 判定方法の選択肢は §8 Q6 で確認する。

### 5.3 教材コンテンツの制作量【解釈】— 重要度: 高

- 必要なコード片の数は、おおよそ「概念数 × 言語数 × 設計の種類（適切／不適切） × 操作ステップ数」になる。
  - 例: 10概念 × 3言語 × 2種類 × 3ステップ ＝ **約180個**
- 要求は「**実際の**ソースコード」なので、各コード片がその言語で正しくコンパイル・実行できることを確認する必要がある。Java と C++ は自動で確認できるが、VBA は Excel 上での手動確認になる（その後、要件定義書 K9 で、Claude が Excel を自動操作して確認する形に変更）。
- 言語の切り替え自体は UI としては簡単に作れる。しかし言語を1つ追加するたびに全概念分のコードが要るため、**制作コストは言語数に比例して増える**。
- 教材を誰がどう作り、誰が正確性をレビューするかを決める必要がある → §8 Q7

### 5.4 「GUIの簡単な操作」の具体像【解釈】— 重要度: 高

原文からは操作の形が決まらない。アプリの中心となる体験なので、次工程の前に決める必要がある。考えられる形は次のとおり。

| 案 | 操作の形 | 伝えやすいこと | 制作コスト |
| --- | --- | --- | --- |
| A. 設計の切り替え | 「不適切 ⇔ 適切」をトグルで切り替え、2つのコードの差分を表示する | 概念を適用するとコードがどう変わるか | 低 |
| B. 段階的リファクタリング | ステップ送り（またはスライダー）で、不適切な設計を少しずつ適切な設計に直していく。各ステップの差分と解説を表示する | 改善の手順と、各手順の目的 | 中 |
| C. 変更要求シミュレーション | 「ハイブリッド車を追加する」などの仕様変更を選ぶと、不適切／適切それぞれの設計で必要な修正を差分で並べて表示する | **メリット・使い時**（変更時に修正箇所がどれだけ減るか） | 中 |
| D. 図の直接操作 | クラス図を GUI で編集すると、コードが連動して変わる | クラス間の関係 | 高 |

【決定】A と C の組み合わせを採用する（Q3）。採用理由は次のとおり。

- 概念のメリットは「変更が起きたとき」に現れるので、C はメリットと使い時を最も直接的に示せる。
- デメリットも C の仕組みで示せる。たとえば「変更が起きない場面では、適切な設計のほうがクラスや行数が増えるだけ」という比較を見せればよい。
- 「不適切な設計」に「未適用」だけでなく「**過剰適用**」（不要な抽象化など）を含めると、使うべきでない場面も伝えられる。

### 5.5 原文で触れられていない事項【解釈】

次の事項は原文にないが、アーキテクチャを左右するため確認が必要。

- 誰が使うか、どこまで公開するか（ログイン・サーバ・運用の要否が決まる）→ Q1
- 学習進捗を保存するか、どこに保存するか → Q8
- 対応端末（コード差分を左右に並べるには一定の画面幅が要る）→ Q10
- 費用の上限と期限 → Q11

## 7. スコープ外【決定】

### 7.1 初回リリースには含めないが、将来追加するもの（UR-11）

初回リリースでは作らないが、後から追加できる構成にしておく。

- ログイン・アカウント、端末間での学習データ同期（Q1, Q8）
- 採点機能（初回は自己評価のみ。Q6。方式は要件定義書 RQ11）
- ランキング（基準は要件定義書 RQ13）

### 7.2 作らないもの

- 汎用的なプログラミング入門（変数・制御構文など）。オブジェクト指向に入るための前提知識は扱わない（Q2）
- スマートフォン・タブレット向けの最適化（Q10）
- 学習者同士の交流機能（掲示板など）
- 学習者による教材の投稿・編集
- 講師・管理者による受講管理（Q1）
