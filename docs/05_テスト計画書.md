## 0. この文書の位置づけ

何を、どの段階で、どうやって確かめるかを決める。個々のテストの手順やデータは、実装の工程でテストコードとして書く。

V字モデルの対応は次のとおり。教材の正しさがこのアプリの価値の大部分を占めるため、一般的な4段階に「教材テスト」を加える。

```text
 要件定義（REQ-02） ◀───────────────▶ 受け入れテスト（§7）
   基本設計（DES-01・DES-02） ◀─────▶ システムテスト（§6）・教材テスト（§4）
     詳細設計（DES-03） ◀───────▶ 結合テスト（§5）
       実装 ◀──────────▶ 単体テスト（§3）
```

本書は 2026-10-18 にユーザが確認し、確定した。

## 1. 基本方針

| 方針 | 内容 |
| --- | --- |
| 自動テストを中心にする | Pull Request ごとに CI で全自動テストを実行し、1つでも失敗したら公開しない（DES-03 §9.1） |
| 教材は「動かして」確かめる | 教材のコードは、3言語・すべての状態で実行し、期待結果と照合する（DES-01 §4.1） |
| テスト用の教材を分ける | 単体テストと結合テストでは、本物の教材ではなく、テスト用の小さな教材（`tests/fixtures/content/`）を使う。教材を直しても、プログラムのテストが壊れないようにするため |
| 手動で確かめるものを絞る | 手動は、教材の内容のレビュー、見た目・使いやすさ、公開前の初回表示の測定、本番での通信の確認に限る |
| カバレッジの数値は目標にしない | 数値より、§3 の観点を漏れなく確かめることを重視する。目安として、`src/domain` と `src/build` は行の80%以上を通るようにする（CI では止めない） |

## 6. システムテスト

ビルドしたサイトを、配信時のヘッダ（`_headers`）を反映する方法で手元から配信し、Playwright で3種類のブラウザエンジンから操作する。本物の教材を使う（教材の中身ではなく、画面の動きを確かめる）。

### 6.1 機能

「Must を含む」が ○ のテストは、受け入れテスト AC-02 の対象になる。「実装する場合のみ」は Could の要件で、初回に作らなければ行わない。

| ID | 確かめること | 根拠 | Must を含む |

| ST-01 | トップに6つの概念が推奨順に並び、学習状況が表示される | FR-001, FR-002 | ○ |
| ST-02 | ヘッダ・タブ・関連概念のリンクで移動できる。各タブの URL を直接開ける。ブラウザの「戻る」が効く。存在しない URL では「ページが見つかりません」が出る | FR-003, FR-004, FR-021 | ○ |
| ST-03 | 表示言語を切り替えると、全画面のコードがその言語になる。選んでいる設計と変更要求は保たれる。再訪時に復元され、最初の描画から正しい言語で表示される | FR-010〜012 | ○ |
| ST-04 | VBA の「継承」で、直接表現できない旨の注記と代わりのコードが表示される | FR-013, CR-11 | ○ |

## 9. 不具合の管理

- 不具合は GitHub Issues に記録する（学習者からの誤りの報告と同じ場所）。
- 重要度は次の3段階とする。

| 重要度 | 例 |
| --- | --- |
| 高 | 学習を続けられない、教材の内容やコードが誤っている、学習データが消える、外部に情報が送られる |
| 中 | 一部の機能が使えないが、他の方法で学習を続けられる |
| 低 | 表記の誤り、見た目の崩れ |

- 不具合を直すときは、その不具合を再現するテストを先に追加する。
