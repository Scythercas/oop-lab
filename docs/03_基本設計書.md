## 0. この文書の位置づけ

[要件定義書](02_要件定義書.md)（以下 REQ-02）の要件を、**どのような構成・画面・データで実現するか**を決める（外部設計）。モジュール内部の作りや、データ項目の細かい定義は詳細設計で決める。

変更にコストがかかる技術判断は、[ADR](adr/)（技術判断の記録）に理由と却下した案を残す。

| ADR | 判断 |
| --- | --- |
| [ADR-0001](adr/0001-静的サイトとして配信する.md) | 初回はサーバなしの静的サイトとして配信し、将来のサーバ機能は同じドメインの API として追加する |
| [ADR-0002](adr/0002-ホスティングにCloudflareを使う.md) | ホスティングに Cloudflare を使う |
| [ADR-0003](adr/0003-フロントエンドにAstroとReactを使う.md) | フロントエンドに Astro・React・TypeScript を使う |
| [ADR-0004](adr/0004-教材をファイルで管理し差分をビルド時に計算する.md) | 教材はリポジトリ内のファイルで管理し、差分と修正量はビルド時に計算する |
| [ADR-0005](adr/0005-VBAの動作確認をローカルで自動化する.md) | VBA の動作確認はユーザの PC で自動実行し、その記録を CI で照合する |

教材の中身（概念ごとの題材・仕様・設計バリエーション・変更要求・実装課題）は、[教材コンテンツ仕様書](03-2_教材コンテンツ仕様書.md) に分けて定める。REQ-02 付録A で「基本設計で確定する」とした内容である。

本書と ADR は、2026-10-16 にユーザが確認し、確定した。ユーザの決定に基づく箇所は、REQ-02 の ID などで出典を示す。

## 1. 全体構成

### 1.1 初回リリースの構成

```text
【教材の作成から公開まで】

 [Claude（ユーザの PC 上）]
   │ ① 教材をブランチで作成・修正
   │ ② VBA 確認ツール（PowerShell ＋ Excel）で VBA を実行確認し、確認記録を残す
   ▼
 [GitHub リポジトリ（公開）] ──③ Pull Request──▶ [GitHub Actions（CI）]
                                                   ├ 教材データの検証（形式・ID・件数）
                                                   ├ Java・C++ のコンパイル・実行・出力の照合
                                                   ├ VBA 確認記録の照合
                                                   ├ 差分・修正量の計算、ページの生成
                                                   └ デプロイ（PR → プレビュー URL ／ main → 本番）
                                                           ▼
 [ユーザ] ④ プレビュー URL と PR で教材をレビュー → main にマージ
                                                           ▼
                                           [Cloudflare（静的配信・HTTPS）]
                                                           ▼
                                           [学習者のブラウザ]

【学習者のブラウザ内】

 ┌ 生成済みの静的ページ（解説・コード・差分・修正量は HTML／JSON として生成済み）
 ├ 対話部品（React）… 表示言語の切り替え、設計の切り替え、変更要求の選択、クイズ、エディタ、進捗表示 など
 ├ 学習データストア … 学習データの読み書きを一手に引き受ける（保存先: localStorage）
 └ クイズの判定     … 正解データ（クイズ画面でだけ読み込む）と照合する
```

実行時にサーバ側の処理はない。外部との通信は、ページと教材データの取得だけである。

### 1.2 構成要素

| 構成要素 | 役割 | 技術 | 根拠 |
| --- | --- | --- | --- |
| 教材データ | 解説・コード・変更要求・設問・課題 | YAML・Markdown・各言語のソースファイル | ADR-0004 |
| サイト生成 | 教材を検証し、差分・修正量・ハイライト済みコードを含むページを生成 | Astro・TypeScript | ADR-0003, ADR-0004 |
| 対話部品 | 画面内の操作（表示言語の切り替え、設計の切り替え、変更要求の選択、クイズ、エディタ、「読み終えた」、進捗表示、学習データの管理） | React（Astro のアイランド） | ADR-0003 |
| 学習データストア | 学習データの保存・読み込み・形式の移行 | TypeScript ＋ localStorage | NFR-15 ① |
| CI | 教材の検証、コードの実行確認、サイト生成、デプロイ | GitHub Actions | NFR-10, NFR-13 |
| VBA 確認ツール | VBA の取り込み・実行の確認と記録 | PowerShell ＋ Excel（COM 経由） | ADR-0005 |
| 配信 | 静的ファイルの HTTPS 配信、PR ごとのプレビュー | Cloudflare | ADR-0002 |

### 1.3 外部依存

| 依存先 | 用途 | 止まったときの影響 | 代替のしやすさ |
| --- | --- | --- | --- |
| Cloudflare | 配信 | サイトが表示できない（学習データは手元に残る） | 高い。静的ファイルなので、他の静的ホスティングに移せる |
| GitHub（リポジトリ・Actions・Issues） | 版管理・CI・誤り報告 | 教材の更新と公開ができない。公開中のサイトには影響しない | 中。CI の定義を書き直せば移せる |
| npm のライブラリ | サイト生成・画面部品 | ビルド時のみ影響 | ライブラリごとに異なる（詳細設計で一覧化） |
| Excel（ユーザの PC） | VBA の動作確認 | VBA 教材の更新が止まる。公開中のサイトには影響しない | 低い。代替は手作業での確認だが、NFR-10・AC-03 の変更になるため、その場合はユーザに相談する |

### 1.4 将来の拡張（ログイン・採点・ランキング）の取り付け位置

初回には作らないが、追加するときに次の位置へ取り付ける（NFR-15、ADR-0001）。

```text
 [ブラウザ] ──同じドメインの /api/*──▶ [API（Cloudflare Workers）] ──▶ [データベース（Cloudflare D1）]
                                              ├▶ 認証（方式は将来決める）
                                              └▶ 採点（方式は将来決める: 実行環境 ／ AI の API）
```

| 将来の機能 | 初回から用意しておくもの | 追加時に変えるもの |
| --- | --- | --- |
| ログイン・端末間同期 | 学習データストアに読み書きを集約。学習データに形式の版番号を付ける | サーバとの同期の仕組みを足し、ブラウザの学習データをアカウントに取り込む処理を足す（ADR-0006 により、保存先の切り替えではなく同期とした） |
| ランキング | 設問と正解を別ファイルにする | 正解データを公開ページから外し、判定を API に移す |
| 採点 | 実装課題の評価結果に評価方法（自己評価／採点）を持たせる | 下の表の方式に応じて、採点の処理と結果表示を足す |

採点の方式は未定（REQ-02 RQ11）なので、3つの方式それぞれの取り付け位置を決めておく。

| 方式 | 取り付け位置 | API キーなどの秘密情報 | 費用の負担 |
| --- | --- | --- | --- |
| コードを実行して採点 | API から、別に用意するコード実行環境（コンテナなど）を呼ぶ | 実行環境の認証情報を API 側のシークレットに置く | 運営者 |
| AI が採点（運営者負担） | API から AI の API を呼ぶ | AI の API キーを API 側のシークレットに置く。ブラウザには渡さない | 運営者 |
| AI が採点（学習者がキーを用意） | ブラウザから AI の API を直接呼ぶ。運営者のサーバを通さない | 学習者のキーは学習者のブラウザ内だけに置き、運営者には送らない | 学習者 |

費用の上限は、外部 API の料金を含めて月額5,000円（REQ-02 RQ12, CON-02）。Cloudflare の有料プラン（月額5ドル程度から）だけなら上限に収まる見込み。採点で運営者が負担する費用（実行環境・AI の API）は、方式を決める時点で見積もり直し、上限に収まるかを確かめる。

## 2. 技術選定

| 対象 | 採用 | 主な理由 | 記録 |
| --- | --- | --- | --- |
| 配信方式 | 静的サイト（ビルド時に全ページ生成） | 運用費0円、障害点が少ない、表示が速い | ADR-0001 |
| ホスティング | Cloudflare | 静的配信が無料、PR ごとのプレビュー、将来のサーバ機能を同じ基盤で足せる | ADR-0002 |
| サイト生成 | Astro | 教材中心のサイトに向く。ページごとに必要な JavaScript だけを配る。教材データの形式検証の仕組みを持つ | ADR-0003 |
| 対話部品 | React | 利用者が多く、保守しやすい。将来のログイン画面などの部品も揃っている | ADR-0003 |
| 言語 | TypeScript | 教材データ・学習データの形を型で守れる | ADR-0003 |
| コードの色付け | Shiki（ビルド時） | Java・C++・VBA に対応する文法定義があり、実行時の処理が要らない | ADR-0004 |
| 差分の計算 | 行単位の差分ライブラリ（ビルド時） | 差分表示と修正量を同じ計算結果から出せる（NFR-12） | ADR-0004 |
| エディタ（実装課題） | CodeMirror 6 | 軽量で、必要な画面でだけ読み込める（NFR-05） | — |
| CI | GitHub Actions | 公開リポジトリなら無料 | — |
| VBA の確認 | PowerShell ＋ Excel（COM） | ユーザの PC でだけ実行できる | ADR-0005 |

#### 教材コードの確認環境

| 言語 | 確認に使う環境 | 教材の書き方の方針 |
| --- | --- | --- |
| Java | Java 21（LTS） | 古い環境の学習者も読めるよう、新しい構文（レコード、パターンマッチなど）は必要以上に使わない |
| C++ | C++17（GCC）。例外を無効にしてコンパイルする | REQ-02 CR-15 のとおり、動的メモリ確保と例外を使わない。例外はコンパイル時に検出する。動的メモリ確保は、実行時の検出（確保が起きたら失敗にする）と、ソースの文字列検査で CI が見つける（方法の詳細は詳細設計） |
| VBA | Excel for Microsoft 365（Windows） | 標準モジュールとクラスモジュールで構成する。出力は `Debug.Print` を1つの式で書く。`MsgBox` など画面を出す命令は使わない（§9.2、K19） |

### 3.2 画面遷移

```text
 SC-01 トップ ─┬─▶ SC-02a〜e 概念ページ（タブで a〜e を相互に移動。関連概念から他の概念へ）
               ├─▶ SC-03 学習データ
               └─▶ SC-04 このサイトについて

 ・すべての画面のヘッダから SC-01・SC-03 へ、フッタから SC-04 へ移動できる（FR-003）
 ・表示言語の切り替えはヘッダにあり、ページを移動しない（FR-010, FR-011）
```

### 3.3 共通レイアウト

```text
┌──────────────────────────────────────────────────────────────────────────
│ オブジェクト指向ラボ   概念一覧   学習データ           表示言語 [ Java | C++ | VBA ]
├──────────────────────────────────────────────────────────────────────────
│ （各画面の本体）
├──────────────────────────────────────────────────────────────────────────
│ このサイトについて ／ 誤りを報告する（GitHub Issues） ／ ライセンス
└──────────────────────────────────────────────────────────────────────────
```

- 表示言語の初期値は Java。選んだ言語はブラウザに記憶する（FR-012）。
- 表示言語の切り替えは、ページ内に埋め込んだ3言語分の表示を切り替えるだけで、通信しない（NFR-05 の0.5秒以内）。
- 記憶した言語がページ表示の一瞬後に切り替わる「ちらつき」を防ぐため、ページの最初で言語を決めてから描画する（方法は詳細設計）。

### 3.6 SC-02a 解説

```text
│ 定義 ／ 目的 ／ メリット ／ デメリット ／ 使い時 ／ 使わない方がよい時 ／ よくある誤り ／ 関連概念
│ （8要素を見出しで区切って表示。関連概念は他の概念ページへのリンク）
│
│ ┌ C++ での補足 ─────────────────────────────
│ │ （表示言語に応じた補足。例: 動的メモリ確保を使わない理由、virtual が必要な理由）
│ └─────────────────────────────────────────
│                                              [ 読み終えた ]
```

- 「解説を読んだ」は、学習者が「読み終えた」を押したときに記録する（FR-070。REQ-02 では基本設計で決めるとしていた）。
- 言語ごとの補足は、選んでいる表示言語のものだけを表示する（FR-022）。

### 3.7 SC-02b 設計比較

```text
│ 題材: シフト位置（P・R・N・D）の管理                       仕様を見る ▼
│ 比較する設計:  左 [ 未適用 ▼ ]   右 [ 適切 ▼ ]            差分の表示: (●)左右 ( )1列
│ ファイル:  Main.java（変更）  Transmission.java（変更）  ShiftPosition.java（追加）
│ ┌ 未適用  2ファイル・2クラス・40行 ─────┐ ┌ 適切  3ファイル・3クラス・58行 ─────┐
│ │ 12   tm.position = "P";              │ │ 12   tm.shiftTo(ShiftPosition.P, 0); │
│ │ 13 - tm.position = "D";              │ │ 13 + if (!tm.shiftTo(...)) {         │
│ │ …                                    │ │ …                                    │
│ └──────────────────────────────────────┘ └──────────────────────────────────────┘
│ ▼ この設計の問題点（未適用）              ▼ この設計の良い点（適切）
```

- 比較する2つの設計は、選択欄で選ぶ。既定は左「未適用」、右「適切」。「過剰適用」がない概念では選択肢に出さない（FR-031, FR-032）。
- ファイルは、同じ言語の中でファイル名によって対応づけ、「追加」「削除」「変更」「変更なし」を一覧で示す。選んだファイルの左右を並べ、行の追加・削除を色と記号（`+` ／ `-`）で示す（FR-033, FR-034, NFR-08）。最初に表示するファイルは、変更行数が最も多いファイルとする。
- 規模（ファイル数・クラス数・行数）を設計ごとに表示する（FR-035）。
- 表示言語ではその概念を直接表現できない場合は、コードの上に注記を出す（FR-013。例: VBA の継承）。

### 3.8 SC-02c 変更シミュレーション

```text
│ 変更要求:  (●) 走行中は P に入れない
│            ( ) 試験用に、検証なしで任意のシフト位置を設定できるようにする
│ 比較する設計:  [ 未適用 ▼ ]  と  [ 適切 ▼ ]
│ ┌ 未適用 ──────────────────────────┐ ┌ 適切 ───────────────────────────┐
│ │ 修正量: 2ファイル・4箇所          │ │ 修正量: 1ファイル・1箇所          │
│ │         +10行  -2行               │ │         +4行  -0行                │
│ │ ファイル: [ Main.java ▼ ]         │ │ ファイル: [ Transmission.java ▼ ] │
│ │ （変更前 → 変更後の差分を1列で）   │ │                                   │
│ └───────────────────────────────────┘ └───────────────────────────────────┘
│ 修正行数（追加＋削除）:  未適用 ████████████ 12行   適切 ████ 4行
│ ▼ 解説: 差が出た理由 ／ 修正漏れが起きやすい箇所 ／ この変更から分かること
```

- 変更要求は1件だけ選べる。選び直すと、題材の初期状態に新しい変更要求を当てた結果を表示する（FR-045）。
- 各設計の枠の中は、変更前と変更後の差分を1列で表示する（左右に2つの枠を並べるため、枠の中まで左右に分けると画面幅が足りない）。
- 修正量（変更ファイル数・変更箇所数・追加行数・削除行数）は、表示している差分と同じ計算結果から出す（FR-042, NFR-12）。それぞれの意味は次のとおり（細かい数え方は詳細設計）。
  - 変更ファイル数: 追加・削除・変更されたファイルの数。新しく追加したファイルも数える
  - 変更箇所数: 連続して変わった行のかたまりの数
  - 追加行数・削除行数: 追加・削除された行の数
- 2つの設計を比べる棒グラフと、変更要求の期待（REQ-02 CR-05）との照合には、**修正行数＝追加行数＋削除行数** を使う。4つの数値もすべて表示する。
- 「過剰適用」がある概念では、その変更後のコードも用意し、比較の選択肢に出す（DQ1）。

### 3.9 SC-02d クイズ

```text
│ 問題 3 / 10                                        正解 2 ・ 不正解 0
│ 次のコードで、カプセル化の観点から最も問題がある箇所はどれか。
│ ┌（表示言語のコード）
│ └
│ ( ) A. …   ( ) B. …   ( ) C. …   ( ) D. …
│                                                    [ 解答する ]
│ ── 解答後 ──
│ ✕ 不正解。正解は C
│ 解説: C が正しい理由 ／ A・B・D が誤りである理由
│                                   [ 次の問題へ ]
│ （終了後）結果のまとめ  [ 間違えた問題だけ解き直す ]
```

- 正解データは、クイズ画面でだけ読み込む。解答のたびに照合し、設問ごとの最新の正誤を保存する（FR-051, FR-053, NFR-15 ③）。

### 3.10 SC-02e 実装課題

```text
│ 課題: 未適用の設計のコードを、カプセル化を使って書き直し、追加の仕様も満たしてください。
│ 追加の仕様: N から D に入れるときは、ブレーキを踏んでいること
│ 実装言語: [ Java ▼ ]（Java ／ C++ ／ VBA ／ その他）
│ ┌ エディタ（開始コード入り。「その他」のときは空）
│ └
│ ※ あなたのコードは実行・採点されず、このブラウザの外にも送られません。評価は自己評価です。
│                                                [ 解答を確認 ]
│ ── 確認後 ──
│ 模範解答（実装言語。「その他」のときは表示言語）
│ 自己チェック:  ☐ シフト位置を外から直接書き換えられない   (できた / できなかった)
│                ☐ …
```

- エディタは、この画面を開いたときにだけ読み込む（NFR-05）。
- 書いたコードは、課題と実装言語の組み合わせごとに自動保存する（FR-064）。
- 実装言語の選択欄の初期値は、その課題を初めて開いたときの表示言語とする。その後は学習者が選んだ言語を課題ごとに記憶し、表示言語を切り替えても変えない（書きかけの下書きが入れ替わらないようにするため）。
- 模範解答は、「解答を確認」の直後は実装言語（「その他」なら表示言語）で表示する。その後は、表示言語の切り替えに合わせて模範解答の言語も切り替わる（FR-066）。

### 3.11 SC-03 学習データ

```text
│ 学習の記録
│  概念ごとの状況（解説・クイズの正答数・課題の自己評価）
│ 記録の保存場所について
│  ・このブラウザ内にだけ保存されます。別のブラウザや端末には引き継がれません。
│  ・ブラウザのデータを消すと、記録も消えます。
│ [ 記録をファイルに書き出す ]  [ ファイルから読み込む ]   … Could（FR-073）
│ [ 記録をすべて消す ]（確認あり）
```

利用規約（免責事項を含む）、プライバシーポリシー、ライセンス（本アプリの教材・プログラム、使っているオープンソースソフトウェア）、誤りの報告先（GitHub Issues）を1ページにまとめる（FR-080〜083）。文面は詳細設計で作る。

## 4. データ設計

### 4.1 教材データ

**真実の情報源はリポジトリ**（REQ-02 §8.1）。教材はファイルとして置き、ビルド時に読み込む（ADR-0004）。

```text
content/
├── languages.yaml                         … 表示言語の一覧（ID・表示名・並び順・色付けとエディタの指定・CI でのビルドと実行の方法）
└── concepts/
    └── encapsulation/                     … 概念ID ごとのフォルダ
        ├── concept.yaml                   … 名前・順番・題材・仕様・関連概念
        ├── expected-output.txt            … 題材の初期状態の、期待する実行結果
        ├── explanation.md                 … 解説（8要素を見出しで区切る）
        ├── notes/{言語}.md                … 言語ごとの補足・直接表現できない旨の注記
        ├── variations/{設計}/
        │   ├── commentary.md              … その設計の良い点・問題点
        │   └── {言語}/…                   … ソースファイル一式
        ├── changes/{名前}/                … 名前は変更要求 ID の「.」より後ろ
        │   ├── change.yaml                … タイトル・説明・期待（修正行数の大小）・解説
        │   ├── expected-output.txt        … 変更後の、期待する実行結果
        │   └── {設計}/{言語}/…            … 変更後のソースファイル一式（完全な形）
        ├── quiz/
        │   ├── questions.yaml             … 設問と選択肢。コードを含む設問は言語ごとのコード（正解は含めない）
        │   └── answers.yaml               … 正解と解説
        └── exercises/{名前}/              … 実装課題ごと（名前は課題 ID の「.」より後ろ。初回は1概念1課題）
            ├── exercise.yaml              … 課題文・追加の仕様・自己チェック項目
            ├── expected-output.txt        … 模範解答の、期待する実行結果
            └── answer/{言語}/…            … 模範解答
```

- `{設計}` は `unapplied`（未適用）・`proper`（適切）・`overapplied`（過剰適用）のいずれか。
- `{言語}` は `java`・`cpp`・`vba`。
- 実装課題の開始コードは、`variations/unapplied/{言語}/` をそのまま使う（REQ-02 K6）。課題は「未適用のコードを書き直し、さらに課題専用の追加仕様を1つ満たす」形にする（K20）。そのため模範解答は、設計比較の「適切」とは別のコードになり、自分の期待結果を持つ。
- 変更後のコードは、差分ではなく「変更後の完全なソース」として置く。そのままコンパイル・実行で確認でき、差分はビルド時に計算する。
- 表示言語の追加（NFR-09）は、`languages.yaml` への追記と各フォルダへのソースの追加で行う。画面とビルド処理のプログラムは変えない。ただし、CI の実行環境にその言語の処理系を入れる設定の追加は必要になる（K21）。

#### 主な関係

```text
 概念 1 ── 1 題材・仕様
 概念 1 ── 2〜3 設計（未適用・適切・過剰適用） ── 言語ごとのソース
 概念 1 ── 2以上 変更要求 ── 設計ごと × 言語ごとの変更後ソース
 概念 1 ── 10以上 設問 ── 1 正解・解説
 概念 1 ── 1以上 実装課題 ── 言語ごとの模範解答、3以上の自己チェック項目
```

#### ID の付け方と寿命

| 対象 | 形式（例） | 規則 |
| --- | --- | --- |
| 概念 | `encapsulation` | 一度公開したら変えない |
| 変更要求 | `encapsulation.park-lock` | 同上 |
| 設問 | `encapsulation.q01` | 同上。内容を大きく変えるときは新しい ID にする（古い正誤記録と混ざらないように） |
| 実装課題 | `encapsulation.ex01` | 同上 |
| 自己チェック項目 | `encapsulation.ex01.c1` | 同上 |

学習データはこれらの ID で教材を参照する。削除した ID の記録は無視する（NFR-11）。

#### 期待する実行結果による整合性の確認

同じ仕様を実現するコードは、言語や設計が違っても同じ結果を出すはずである。そこで、題材の初期状態・変更要求・実装課題の模範解答ごとに「期待する実行結果（標準出力）」を1つずつ持ち、**3言語 × すべての設計**の実行結果がそれと一致することを確かめる（REQ-02 CR-09 を強めた確認。§14 K16）。Java と C++ は CI が照合し、VBA は VBA 確認ツールが照合して、その記録を CI が確かめる（§9.2）。クイズ内のコードは、コンパイルできること（VBA は取り込んでコンパイルエラーがないこと）までを確かめる（DQ2）。

また、変更要求には「適切な設計のほうが修正行数が少ない」か「少なくならない（デメリットを示す例）」かの期待を書き、ビルド時に計算した修正行数（§3.8）と照合する（REQ-02 CR-05）。

### 4.2 学習データ

**真実の情報源は学習者のブラウザ**（REQ-02 §8.2）。localStorage の1つのキーに、1つの JSON としてまとめて保存する。

| 項目 | 内容 | 対応要件 |
| --- | --- | --- |
| 形式の版番号 | 学習データの形式の版。形式を変えたら上げ、読み込み時に移行する | NFR-15 ② |
| 設定 | 表示言語 | FR-012 |
| 解説の記録 | 概念ごとに「読み終えた」日時 | FR-070 |
| クイズの記録 | 設問ごとの最新の正誤と日時 | FR-053 |
| 課題の下書き | 課題 × 実装言語ごとのコードと、課題ごとに選んだ実装言語 | FR-064 |
| 課題の評価 | 課題ごと、評価方法（初回は「自己評価」のみ）ごとに、チェック項目ごとの結果と日時 | FR-067, NFR-15 ④ |

- 個人を特定できる情報は持たない。
- 項目の正確な形と、下書きの大きさの上限は詳細設計で決める。
- 学習データの読み書きは「学習データストア」だけが行う。画面の部品は直接 localStorage に触らない（NFR-15 ①）。
- 複数のタブで同時に開いても記録が消えないよう、学習データストアは書き込む直前に最新の内容を読み直し、変更した項目だけを反映して書き戻す。他のタブでの変更は、ブラウザの通知（storage イベント）で受け取って表示を更新する。

## 6. 主要な処理の流れ

### 6.1 教材の追加・修正から公開まで（UC-10）

1. Claude がブランチを作り、教材ファイルを追加・修正する。
2. VBA のソースを変えた場合、Claude が VBA 確認ツールを実行し、確認記録を更新する（§9.2）。
3. Pull Request を作る。CI が教材の検証・Java と C++ の実行確認・VBA 確認記録の照合・ページ生成を行い、プレビュー URL にデプロイする。
4. ユーザが、プレビュー URL の実際の画面と PR の差分で内容をレビューする（REQ-02 CR-13）。
5. ユーザが承認して main にマージすると、CI が本番にデプロイする。

### 6.2 ページの生成（ビルド時）

1. 教材ファイルを読み込み、形式・ID・件数・参照先を検証する。
2. 設計の組み合わせごと、変更要求ごとに、ファイル単位・行単位の差分を計算する。
3. 同じ差分から修正量と規模を計算し、変更要求の「期待」と照合する。
4. コードを色付けし、言語ごとの表示を含むページを生成する。

### 6.3 表示言語の切り替え（UC-05）

1. 学習者がヘッダで言語を選ぶ。
2. 画面は、埋め込み済みのその言語の表示に切り替える。選んでいる設計と変更要求はそのまま保つ（FR-011）。表示するファイルは、言語によってファイル構成が違うため、その差分で変更行数が最も多いファイルを選び直す。
3. 実装課題の画面では、模範解答の表示だけを切り替え、実装言語の選択と下書きは変えない（§3.10）。
4. 学習データストアに言語を保存する。

## 7. 異常系

| 失敗する箇所 | 起きること | 振る舞い | 気づき方 |
| --- | --- | --- | --- |
| localStorage が使えない（プライベートモード、設定で無効など） | 記録を保存できない | 学習は続けられるようにし、画面上部の帯で知らせる。記録はそのページを表示している間だけ持つ（別のページに移ると消える） | 学習者: 帯の表示 |
| localStorage の容量不足 | 下書きなどを保存できない | 保存できなかったことを帯で知らせる。既存の記録は消さない | 同上 |
| 学習データが壊れている（JSON として読めない・形が違う） | 記録を読めない | 壊れた中身を別のキーに退避してから初期化し、帯で知らせる | 同上 |
| 学習データの版が、アプリが知っている版より新しい | 古いアプリで新しい形式を読む（キャッシュなど） | 読み込まず、上書きもしない。その間の記録はそのページを表示している間だけ持つ。再読み込みを促す | 同上 |
| 複数のタブで同時に記録する | 古い内容で書き戻すと、別のタブの記録が消える | 書き込む直前に読み直し、変更した項目だけを反映する（§4.2） | — |
| 学習データの版が古い | — | 読み込み時に新しい形式へ移行する | — |
| 学習データが、削除済みの設問などを参照している | — | その記録は無視する（NFR-11） | — |
| 読み込もうとしたファイルが不正 | — | 読み込まない。今ある記録はそのまま | 学習者: 理由の表示 |
| JavaScript が動かない | 対話部品が動かない | 解説とコード（既定の言語）は読める。対話部品の場所に「JavaScript を有効にしてください」と表示する | 学習者: 表示 |
| 教材データの不正（ビルド時） | ページを作れない | ビルドを失敗させ、公開しない | CI の失敗通知（GitHub からのメール） |
| Java・C++ のコンパイル失敗、実行結果が期待と違う | 誤った教材を公開しうる | ビルドを失敗させ、公開しない | 同上 |
| VBA 確認記録と、現在の VBA ソースまたは期待結果が一致しない | 未確認の VBA を公開しうる | ビルドを失敗させ、公開しない | 同上 |
| 配信先の障害 | サイトが表示できない | 何もしない（静的配信のため、復旧を待つ）。学習データはブラウザに残る | 学習者・運営者 |

#### データの破損・消失時の復旧

- 教材データ: リポジトリの履歴から戻せる。公開サイトは、main を戻せば CI が再デプロイする。
- 学習データ: サーバに控えがないため、学習者がファイルに書き出していない限り復旧できない（REQ-02 §8.2）。壊れていた場合は退避した中身を残す。

## 9. 運用

### 9.1 公開・ロールバック

- 公開: main へのマージで CI が自動デプロイする。手作業はマージだけ（NFR-13）。
- プレビュー: Pull Request ごとにプレビュー URL を作り、レビューに使う。
- ロールバック: main で問題のコミットを取り消すと、CI が再デプロイする。急ぐ場合は Cloudflare の管理画面で直前のデプロイに戻す。
- 費用: 初回は Cloudflare・GitHub とも無料の範囲で運用する（NFR-01）。

### 9.2 VBA の動作確認（ADR-0005）

1. Claude が VBA 確認ツールを実行する。
2. ツールは、確認の対象（VBA のソースと期待結果）を一時フォルダに写し、写しの中でだけ次の加工をする。リポジトリのソースは、学習者に見せる形のまま変えない。
   - `Debug.Print` を、出力を集める手続きの呼び出しに置き換える（`Debug.Print` の出力は外から取り出せないため）
   - 文字コードを、Excel が取り込める形（Shift_JIS）に変える（リポジトリは UTF-8）
   - クラスモジュールに、取り込みに必要な見出し行を付ける
3. Excel の設定を有効にし、確認用の新しいブックに写しを取り込み、実行の入口を呼び出す。
4. 集めた出力を期待結果と照合し、エラーの有無と照合結果を記録する。
5. 終了時（失敗時を含む）に Excel の設定を無効に戻し、確認用のブックは保存せずに閉じる。
6. 確認した VBA ソースと期待結果のハッシュ値、結果、Excel の版、日時を、確認記録ファイルとしてリポジトリに入れる。
7. CI は、現在の VBA ソースと期待結果のハッシュ値が確認記録と一致し、結果が成功であることを確かめる。一致しなければ公開しない。

この置き換えを確実にするため、教材の VBA は出力を `Debug.Print` に1つの式で書く（`;` や `,` で区切らない）。`MsgBox` など画面を出す命令は使わない（K19）。

### 9.3 異常の検知

| 対象 | 気づき方 |
| --- | --- |
| CI の失敗 | GitHub からの通知（メール） |
| 教材の誤り | 学習者からの GitHub Issues |
| 配信の障害 | 実行時の監視は置かない（静的配信のため影響範囲が限られる）。必要になったら外部の死活監視を検討する |

## 12. 変更容易性・やめ方

| 項目 | 内容 |
| --- | --- |
| 変わりそうな箇所 | 教材（最も頻繁）、表示言語の追加、概念の追加（第2弾）、将来のサーバ機能（§1.4） |

## 13. 過剰設計の点検

| 点検項目 | 結果 |
| --- | --- |
| 実装が1つしかない抽象化をしていないか | 学習データストアとクイズの判定は、初回は実装が1つ（ブラウザ内）だが、将来サーバ側の実装に差し替えることがユーザの指示（UR-11）で決まっているため、抽象化を残す。それ以外には作らない |
| 使われない設定・機能を作っていないか | 採点・ランキング・ログインの画面や API は作らない。取り付け位置（§1.4）だけを決める |
| 自前で足りる用途にライブラリを入れていないか | 差分計算・色付け・エディタは自作すると大きいので、実績のあるライブラリを使う。それ以外（状態管理など）にはライブラリを入れず、React の標準機能で済ませる |
| 設計書の分量が実装を上回っていないか | 教材の制作量が大きいアプリなので、文書は「教材の形と確認の仕組み」に重点を置いた |
