## 0. この文書の位置づけ

[要求定義書](01_要求定義書.md)（以下 REQ-01）で確定した要求を、システムが満たすべき条件（要件）に落とし込む。

- 本書で決めるのは「**何を満たすか**」。
- 「**どう作るか**」（技術選定・画面レイアウト・データ形式など）は基本設計で決める。

優先度は次の3段階で表す。

| 優先度 | 意味 |
| --- | --- |
| Must | 初回リリースに必須 |
| Should | 初回リリースで対応したい。工数が足りなければ次回に回す |
| Could | 余裕があれば対応する |

## 1. システム概要

### 1.1 一言で

オブジェクト指向の概念ごとに、**車載の題材を使って、「概念を使わない設計」「適切な設計」「やりすぎた設計」のコードを GUI で切り替えて比べ、仕様変更が来たときの修正量の違いを差分で体感できる**、一般公開の無料 Web アプリ。

### 1.2 前提となる決定事項

| 項目 | 決定内容 | 出典 |
| --- | --- | --- |
| 公開範囲 | 一般公開・ログインなし | REQ-01 Q1 |
| 学習者 | 車載に関わる人（新人や関連部署を含む）。基本文法は書けるが、オブジェクト指向は初心者 | REQ-01 Q2, 本書 RQ8 |
| C++ の書き方 | 車載組込みを意識する（動的メモリ確保と例外を使わない） | 本書 RQ9 |
| 題材 | 車載に限定する | REQ-01 UR-10 |
| GUI 操作 | 設計の切り替え ＋ 変更要求シミュレーション | REQ-01 Q3 |
| 初回の概念 | 基礎の6概念 | REQ-01 Q4 |
| 実装課題の評価 | 模範解答＋自己チェックリストによる自己評価のみ（AI・自動採点なし） | REQ-01 Q6 |
| 教材 | Claude が下書きし、ユーザがレビューする | REQ-01 Q7 |
| 学習データ | ブラウザ内にだけ保存 | REQ-01 Q8 |
| 表示言語 | 初回は Java・C++・VBA | REQ-01 Q9 |
| 端末・UI 言語 | PC のみ・日本語のみ | REQ-01 Q10, Q12 |
| 費用 | 無料（月額0円） | REQ-01 Q11 |
| リポジトリ | 公開する | 本書 RQ1 |
| ライセンス | 教材は CC BY 4.0、プログラムとサンプルコードは MIT | 本書 RQ2 |
| 将来の拡張 | ログイン・採点機能・ランキングを将来追加する。初回には含めないが、作り直さずに追加できる構成にする。採点の方式とランキングの基準は未定 | REQ-01 UR-11, 本書 K10, RQ11, RQ13 |
| 将来機能の費用 | 将来機能を追加した後は、月額5,000円まで費用をかけてよい（初回リリースは月額0円） | 本書 RQ12 |
| VBA の動作確認 | Claude がユーザの PC の Excel を自動操作して行う | 本書 K9 |

### 1.3 学習の流れ（イメージ）

```text
[概念一覧] ─選ぶ→ [概念ページ]
                    ├─ ① 解説        … 定義・目的・メリット・デメリット・使い時 など
                    ├─ ② 設計比較    … 未適用 ⇔ 適切 ⇔ 過剰適用 を切り替え、コードと差分を見る
                    ├─ ③ 変更シミュレーション … 仕様変更を選び、設計ごとの修正量を比べる
                    ├─ ④ 択一クイズ  … 知識の確認
                    └─ ⑤ 実装課題    … 好きな言語で書き、模範解答と自己チェックで確認
                  （どの画面でも表示言語 Java / C++ / VBA を切り替えられる）
```

## 2. 用語定義

REQ-01 §2 の用語に、次を追加する。

| 用語 | 定義 |
| --- | --- |
| 車載 | 自動車に搭載される機能・装置・ソフトウェア（例: センサ、メーター表示、運転支援機能） |
| 題材 | 概念ごとに使う例題のテーマ。車載に限定する（例: タイヤ空気圧の監視）。設計比較・変更シミュレーション・実装課題で共通に使う |
| 設計バリエーション | 同じ題材・同じ仕様を実現する、設計の異なるコード。「未適用」「適切」「過剰適用」の3種類がある |
| 未適用 | 概念を使っていない設計 |
| 適切 | 概念を適切に使った設計 |
| 過剰適用 | 必要以上に、または誤って概念を使った設計（誤用を含む） |
| 変更要求 | 題材に対する仕様変更（例:「ハイブリッド車を追加する」）。変更シミュレーションで使う |
| 修正量 | 変更要求に対応するために必要な修正の量。変更ファイル数・変更箇所数・追加行数・削除行数で表す |
| 学習モード | 概念ページ内の5つの学習方法（解説・設計比較・変更シミュレーション・択一クイズ・実装課題） |
| 実装言語 | 学習者が実装課題で使う言語。表示言語に限らず自由に選べる |
| 開始コード | 実装課題の出発点として渡すコード（通常は「未適用」の設計） |
| 教材データ | 解説・コード・変更要求・設問・課題など、運営者が作成するデータ |
| 学習データ | 学習者ごとの進捗・クイズ結果・課題の下書きなど。ブラウザ内にだけ保存する |
| 運営者 | 教材を作成・公開する人（ユーザと Claude） |

> REQ-01 の「不適切な設計」は、本書では「未適用」と「過剰適用」の総称として扱う。

### 4.2 主要ユースケースの記述

#### UC-03 設計を比較する

- 事前条件: 学習者が概念を選んでいる
- 主シナリオ:
  1. 学習者が「設計比較」を開く。
  2. システムは、題材の仕様と、「未適用」「適切」の2つの設計のコードを並べて表示し、両者の差分を強調する。各設計の規模も表示する。
  3. 学習者が比較する組み合わせを切り替える（例:「適切」と「過剰適用」）。
  4. システムは、選ばれた2つの設計のコードと差分を表示する。
  5. システムは、それぞれの設計の良い点・問題点の解説を表示する。
- 代替シナリオ:
  - 3a. その概念に「過剰適用」がない場合、システムは切り替えの選択肢に「過剰適用」を出さない。
- 例外シナリオ:
  - 2a. 表示言語ではその概念を直接表現できない場合（例: VBA の継承）、システムはその旨と理由を注記し、代替表現のコードを表示する。

#### UC-04 変更要求をシミュレーションする

- 事前条件: 学習者が概念を選んでいる
- 主シナリオ:
  1. 学習者が「変更シミュレーション」を開く。
  2. システムは、その概念の変更要求の一覧を表示する。
  3. 学習者が変更要求を1つ選ぶ。
  4. システムは、2つの設計（既定は「未適用」と「適切」）それぞれについて、変更前後の差分を並べて表示する。
  5. システムは、それぞれの修正量を比較できる形で表示する。
  6. システムは、修正量に差が出た理由、修正漏れが起きやすい箇所、この変更から分かるメリット・デメリットの解説を表示する。
- 代替シナリオ:
  - 4a. 学習者が比較する設計を切り替える（「過剰適用」を含む）。システムは選ばれた設計の差分と修正量に表示を更新する。
  - 3a. 学習者が別の変更要求を選ぶ。システムは、変更前の状態（題材の初期状態）に新しい変更要求を適用した結果を表示する。変更要求は積み重ねない。

#### UC-05 表示言語を切り替える

- 主シナリオ:
  1. 学習者が画面上部で表示言語を選ぶ。
  2. システムは、いま表示している概念・学習モード・選択中の設計や変更要求を保ったまま、コード・差分・修正量・言語ごとの補足を選ばれた言語の内容に更新する。
  3. システムは、選ばれた言語をブラウザに記憶し、次回の訪問時に復元する。

#### UC-07 実装課題に取り組み、自己評価する

- 事前条件: 学習者が概念を選んでいる
- 主シナリオ:
  1. 学習者が「実装課題」を開く。
  2. システムは、課題文（満たすべき仕様）と、実装言語の選択欄（既定値は表示言語）、開始コードを表示する。
  3. 学習者がエディタでコードを書く。システムは書いている内容をブラウザに自動保存する。
  4. 学習者が「解答を確認」を押す。
  5. システムは、模範解答と自己チェックリストを表示する。
  6. 学習者が、チェックリストの各項目を「できた／できなかった」で自己評価する。
  7. システムは自己評価の結果をブラウザに保存する。
- 代替シナリオ:
  - 2a. 学習者が実装言語に表示言語以外（「その他」）を選んだ場合、システムは開始コードを表示しない。学習者は課題文だけを見て書く。
  - 5a. 学習者が表示言語を切り替えると、システムは他の言語の模範解答を表示する。
- 補足: システムは学習者のコードを実行・採点せず、外部にも送信しない。

## 6. 教材コンテンツ要件

教材はこのアプリの価値の大部分を占めるため、機能とは別に要件を定める。

| ID | 要件 | 優先度 |
| --- | --- | --- |

| CR-03 | 解説は FR-020 の8要素をすべて含む | Must |
| CR-04 | 設計バリエーションは「未適用」「適切」を必須とする。「過剰適用」は、自然な例が作れる概念で用意する | Must |

## 10. スコープ外

## 付録A. 概念ごとの題材と設計バリエーションのイメージ（参考）

レビューしやすくするためのイメージ。確定した内容は [教材コンテンツ仕様書](03-2_教材コンテンツ仕様書.md)（DES-02）を正とする。題材はすべて車載とし、実車の仕組みを簡略化したモデルを使う（CR-14）。

| 概念 | 題材（案） | 未適用 | 適切 | 過剰適用 | 変更要求の例 |
| --- | --- | --- | --- | --- | --- |
| クラスとインスタンス | タイヤ空気圧の監視（4輪それぞれの空気圧センサ） | 4輪分の変数（空気圧・温度）と処理を、輪ごとにばらばらに持つ | タイヤクラスと、輪ごとの4つのインスタンス | 輪ごとに別々のクラスを作る（誤用。DES-02 で追加） | 6輪のトラックにも対応する |
| カプセル化 | シフト位置（P・R・N・D）の管理 | シフト位置を外部から直接書き換えられる | シフト位置を非公開にし、切り替えはメソッド経由で行う（不正な切り替えを拒否する） | すべての項目に機械的に getter / setter を付ける（実質的には直接書き換えと同じ） | 「走行中は P に入れない」ルールを追加する |
| 継承 | 車載センサの共通処理（水温センサ・油圧センサ） | 値の範囲チェックや故障判定を、センサごとにコピーして重複させる | 共通処理を基底クラスにまとめる | 「〇〇は△△の一種」と言えない関係での継承（例: 警告灯がセンサを継承する）、深すぎる継承階層 | 全センサに「故障時は代替値を使う（フェイルセーフ）」処理を追加する |
| ポリモーフィズム | 航続可能距離の計算（ガソリン車・電気自動車） | パワートレイン（動力源）の種類ごとの条件分岐（`switch` / `Select Case`） | 種類ごとのクラスと、共通の型による呼び出し | 種類が増える見込みのない箇所にまで共通の型を用意する | ハイブリッド車を追加する |
| 抽象化 | 警告の出力（メーター表示・警告音） | 警告を出す側が、具体的な出力装置に直接依存する | 警告を出す側は、出力の抽象（インタフェース）にだけ依存する | 実装が1つしかないのにインタフェースを作る | 出力先にヘッドアップディスプレイを追加する |
| コンポジションと委譲 | 運転支援機能の組み合わせ（グレードごとに搭載機能が違う） | 機能の組み合わせごとにサブクラスを作る（継承の乱用） | 運転支援機能を部品として持ち、処理を任せる（委譲） | （なし） | 新機能「車線維持支援」を追加する |

> VBA には継承がないため、「継承」の適切な設計は、委譲と `Implements` による代替表現で示す（FR-013）。
