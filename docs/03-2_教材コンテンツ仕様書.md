## 0. この文書の位置づけ

[要件定義書](02_要件定義書.md)（REQ-02）の付録A で「基本設計の『教材コンテンツ仕様』で確定する」とした、概念ごとの教材の中身を決める。

- 本書で決めるもの: 題材、仕様、設計バリエーションの中身、変更要求、実装課題、言語ごとの注意、クイズの内訳
- 本書で決めないもの: 実際のコード・解説文・設問の文章（教材の制作は実装工程で行い、ユーザがレビューする。REQ-02 CR-13）
- 教材ファイルの置き方は DES-01 §4.1 に従う

本書の数値（空気圧の基準値、換算式など）は学習用に簡略化した値で、実車の値ではない（REQ-02 CR-14）。本書は 2026-10-16 にユーザが確認し、確定した。

## 1. 全概念に共通する決まり

### 1.1 教材の構成（1概念あたり）

| 要素 | 内容 | 根拠 |
| --- | --- | --- |
| 題材と仕様 | 1つの題材と、プログラムが行うことの説明 | CR-02 |
| 期待する実行結果 | 題材の初期状態・変更要求ごと・実装課題の模範解答ごとに1つ | DES-01 §4.1 |
| 設計バリエーション | 未適用・適切（必須）、過剰適用（自然な例が作れる概念だけ） | CR-04 |
| 変更要求 | 2件。1件目は「適切な設計のほうが修正行数が少ない」例、2件目は「少なくならない」例（デメリットや、使わない方がよい時を示す） | CR-05 |
| 実装課題 | 未適用のコードを書き直し、さらに課題専用の追加仕様を1つ満たす。自己チェック項目は3つ | CR-07, DES-01 K20 |
| クイズ | 10問（内訳は §1.4） | CR-06 |

### 1.2 コードの書き方（全言語）

- 入力は使わず、プログラムの中に固定の値として持つ（実行結果を毎回同じにするため）。
- 出力する数値は整数にする。3言語の出力を1文字の違いもなくそろえるためである（小数の表示形式は言語ごとに違う。DES-01 K16）。
- 規模の目安は、1ファイル60行以内、1つの設計バリエーションの合計200行以内（CR-10）。
- 名前の付け方は各言語の慣習に従い、他言語からの直訳調にしない（CR-08）。
- 車載用語は使ってよいが、解説の初出で説明する（CR-02）。実在のメーカー名・製品名は使わない（CR-14）。

### 1.3 言語ごとの決まり

| 言語 | 決まり |
| --- | --- |
| Java | 1クラス1ファイル。実行の入口は `Main.java` の `main`。古い環境の学習者も読めるよう、新しい構文（レコード、パターンマッチなど）は必要以上に使わない（DES-01 K18） |
| C++ | C++17。クラスごとにヘッダファイル1つ（宣言と実装をまとめる）、実行の入口は `main.cpp`（§4 K22-4）。動的メモリ確保（`new`・`malloc`、内部で確保する標準ライブラリのコンテナや文字列など）と例外を使わない。オブジェクトは静的に確保し、参照またはポインタで扱う（CR-15）。配列は `std::array` か固定長の配列を使う |
| VBA | 実行の入口は標準モジュール `Program` の `Sub Main()`。クラスはクラスモジュール。すべてのモジュールに `Option Explicit` を書く。出力は `Debug.Print` に1つの式で書き、`MsgBox` など画面を出す命令は使わない（DES-01 K19）。引数付きのコンストラクタがないため、生成後に初期化用のメソッドを呼ぶ。継承がないため、必要な場合は委譲と `Implements` で代わりに表し、注記する（FR-013） |

## 2. 概念ごとの仕様

### 2.1 クラスとインスタンス（`class-instance`）

| 項目 | 内容 |
| --- | --- |
| 題材 | タイヤ空気圧の監視 |
| 仕様 | 4輪（左前・右前・左後・右後）の空気圧（kPa）と温度（℃）を持つ。空気圧が 200kPa 未満の輪は「空気圧低下」、それ以外は「正常」と表示する |
| 出力の例 | `左前 230kPa 25℃ 正常` ／ `左後 185kPa 27℃ 空気圧低下` |
| 未適用 | 輪ごとに変数（空気圧・温度で8個）を持ち、判定と表示の処理を輪ごとに書き写している。基準値の 200 は1か所の定数にまとめている |
| 適切 | タイヤのクラス（位置・空気圧・温度、空気圧低下の判定、表示）を作り、4輪をそれぞれインスタンスにする |
| 過剰適用（誤用） | 輪ごとに別々のクラス（左前タイヤ、右前タイヤ…）を作る。クラスとインスタンスの取り違え（§4 K22-1） |
| 変更要求1 | `class-instance.six-wheels`: 6輪のトラックにも対応する（後輪を2輪追加）。期待: 適切のほうが少ない |
| 変更要求2 | `class-instance.threshold`: 空気圧低下の基準を 200kPa から 210kPa に変える。期待: 少なくならない（基準値を1か所にまとめる工夫は、クラスがなくてもできる。クラスの効果は「同じ形のデータと処理が複数ある」ときに出る） |
| 実装課題の追加仕様 | 温度が 80℃ を超えた輪は「高温」と表示する（空気圧低下より優先する） |
| 自己チェック | ① 1輪分のデータと処理を1つのクラスにまとめた ② 4輪を、1つのクラスのインスタンスとして作った（輪ごとにクラスを作っていない） ③ 高温の判定を、クラスの中の1か所だけに書いた |
| 言語ごとの注意 | C++: インスタンスは配列として静的に確保する。VBA: 生成後に初期化用のメソッドで位置・空気圧・温度を設定する |

### 2.2 カプセル化（`encapsulation`）

| 項目 | 内容 |
| --- | --- |
| 題材 | シフト位置（P・R・N・D）の管理 |
| 仕様 | シフト位置は P・R・N・D のいずれか。切り替えの要求（位置と、そのときの車速 km/h）を順に処理し、受け付けたか拒否したかと、現在の位置を表示する。初期の規則は「走行中（車速が0でない）は R に入れない」 |
| 出力の例 | `D→R 20km/h 拒否 現在D` |
| 未適用 | シフト位置が外から直接書き換えられる。規則の確認は、書き換える側の各箇所に書かれている |
| 適切 | シフト位置を非公開にし、切り替えは「切り替える」メソッドだけで行う。規則の確認はメソッドの中の1か所にまとめ、受け付け／拒否を戻り値で返す |
| 過剰適用（誤用） | シフト位置を非公開にしたが、検証のない取得・設定のメソッドを機械的に付けた（実質的に、外から自由に書き換えられる） |
| 変更要求1 | `encapsulation.park-lock`: 走行中は P に入れない。期待: 適切のほうが少ない（未適用は、書き換えるすべての箇所に確認を足す必要があり、漏れやすい） |
| 変更要求2 | `encapsulation.test-override`: 試験用に、規則を無視して任意のシフト位置を設定できるようにする。期待: 少なくならない（適切な設計では専用のメソッドを足す必要がある。あわせて、こうした要求そのものがカプセル化を壊すことも解説する。§4 K22-2） |
| 実装課題の追加仕様 | N から D に入れるときは、ブレーキを踏んでいること（要求にブレーキの状態を加える） |
| 自己チェック | ① シフト位置を外から直接書き換えられない ② 切り替えの規則が1か所にまとまっている ③ 拒否したことを、呼び出し側が戻り値で知れる |
| 言語ごとの注意 | C++: 例外を使わず、受け付け／拒否は戻り値で返す。VBA: 値の設定（`Property Let`）は結果を返せないため、切り替えは `Function` で作る |

### 2.3 継承（`inheritance`）

| 項目 | 内容 |
| --- | --- |
| 題材 | 車載センサの共通処理（水温センサ・油圧センサ） |
| 仕様 | 各センサの生の値（AD 変換値 0〜1023）を読み、0 または 1023 なら断線・短絡とみなして「故障」と表示する。それ以外は、センサごとの換算式で物理量（水温 ℃、油圧 kPa）に換算して表示する |
| 出力の例 | `水温センサ 512 → 90℃` ／ `油圧センサ 1023 → 故障` |
| 未適用 | 水温センサと油圧センサのクラスが、範囲の確認・故障判定・表示を、それぞれコピーして持つ |
| 適切 | 共通の処理（範囲の確認・故障判定・表示）を基底クラス「センサ」にまとめ、換算式だけを派生クラスに書く |
| 過剰適用（誤用） | 警告灯が「センサの値を読む処理」を使い回すために、センサクラスを継承する（警告灯はセンサの一種ではない） |
| 変更要求1 | `inheritance.failsafe`: 故障時は、代わりの値（フェイルセーフ値）を使って表示を続ける。期待: 適切のほうが少ない |
| 変更要求2 | `inheritance.water-formula`: 水温センサの換算式だけを変える。期待: 少なくならない（どちらも1か所） |
| 実装課題の追加仕様 | 排気温センサ（AD 値から ℃ への換算式は課題文で示す）を追加する |
| 自己チェック | ① 共通の処理を、基底クラス（VBA では共通の部品）の1か所にだけ書いた ② 派生クラスには、換算式など違う部分だけを書いた ③「排気温センサはセンサの一種」と言える関係になっている |
| 言語ごとの注意 | C++: 基底クラスで差し替える関数は `virtual`、派生クラスでは `override` を付ける。VBA: 継承がないため、適切な設計は「共通の処理を持つ部品クラスに任せる（委譲）＋共通の型（`Implements`）」で表し、過剰適用は「センサではない警告灯が、センサの型を実装する」で表す（§4 K22-3） |

### 2.4 ポリモーフィズム（`polymorphism`）

| 項目 | 内容 |
| --- | --- |
| 題材 | 航続可能距離の計算（ガソリン車・電気自動車） |
| 仕様 | 車両ごとの残量（燃料 L ／ 電池 kWh）と、燃費・電費（km/L ／ km/kWh）から航続可能距離（km、整数に切り捨て）を計算し、残量と一緒に表示する。航続可能距離が 50km 未満なら案内（「給油してください」／「充電してください」）も出す |
| 出力の例 | `ガソリン車 残り20L 航続300km` ／ `電気自動車 残り6kWh 航続36km 充電してください` |
| 未適用 | 距離の計算・残量の単位・案内文の3か所で、動力源の種類によって条件分岐している |
| 適切 | 動力源ごとのクラスと共通の型を作る。呼び出し側は、種類を区別せずに同じ呼び方をする |
| 過剰適用 | 種類によって変わらない処理（距離を「km」で表示する部分）にまで、共通の型と実装クラスを作る |
| 変更要求1 | `polymorphism.hybrid`: ハイブリッド車を追加する。期待: 適切のほうが少ない（未適用は3か所の分岐すべてを直す必要があり、漏れやすい） |
| 変更要求2 | `polymorphism.message`: 表示を「航続○km」から「あと○km 走れます」に変える。期待: 少なくならない（共通の表示処理の1か所。過剰適用では、使い道のない共通の型の分だけ修正が増える） |
| 実装課題の追加仕様 | 水素燃料電池車を追加する（残量は kg、案内は「水素を充填してください」） |
| 自己チェック | ① 動力源の種類による条件分岐がなくなった ② 新しい種類を、既存のクラスを変えずに、クラスの追加だけで足せる ③ 呼び出し側は共通の型だけを使っている |
| 言語ごとの注意 | C++: 純粋仮想関数を持つ基底クラスを作り、静的に確保したオブジェクトへのポインタの配列で扱う。VBA: `Implements` で共通の型を表す |

### 2.5 抽象化（`abstraction`）

| 項目 | 内容 |
| --- | --- |
| 題材 | 警告の出力（メーター表示・警告音） |
| 仕様 | 警告（例:「水温が高い」「半ドア」）が発生すると、登録されたすべての出力先に知らせる。出力先はメーター表示（文字を出す）と警告音（音の種類を鳴らす）で、画面には `[メーター] 水温が高い` ／ `[警告音] ピピッ` のように表示する |
| 未適用 | 警告を管理するクラスが、メーター表示と警告音の具体的なクラスを自分で作り、それぞれ専用のメソッドを呼ぶ |
| 適切 | 「警告の出力先」の抽象（インタフェース）を作り、警告を管理するクラスはそれだけを知る。出力先は外から渡す |
| 過剰適用 | 実装が1つしかなく、変わる見込みもない「警告文の組み立て」にまで、インタフェースを作る |
| 変更要求1 | `abstraction.hud`: 出力先にヘッドアップディスプレイを追加する。期待: 適切のほうが少ない |
| 変更要求2 | `abstraction.timestamp`: 警告文に発生時刻（走行開始からの秒数）を付ける。期待: 少なくならない（過剰適用では、使い道のない抽象の分だけ修正が増える） |
| 実装課題の追加仕様 | 出力先に「走行記録（ドライブレコーダーへの記録）」を追加する |
| 自己チェック | ① 警告を管理するクラスが、具体的な出力先の名前を知らない ② 出力先を外から渡している ③ 新しい出力先を、警告を管理するクラスを変えずに追加できる |
| 言語ごとの注意 | C++: 出力先は静的に確保し、ポインタの固定長配列で持つ。VBA: `Implements` と `Collection` を使う |

ポリモーフィズムとの違いは、解説で次のように説明する: ポリモーフィズムは「同じ呼び方で、種類ごとに違う動きをさせる」こと、抽象化は「依存する相手を抽象にして、具体的な相手を知らずに済ませる」こと。

### 2.6 コンポジションと委譲（`composition`）

| 項目 | 内容 |
| --- | --- |
| 題材 | 運転支援機能の組み合わせ（グレードごとに搭載する機能が違う） |
| 仕様 | グレードごとに、搭載する運転支援機能の組み合わせが違う（ベーシック: 衝突被害軽減ブレーキ、スタンダード: 衝突被害軽減ブレーキ＋アダプティブクルーズコントロール）。走行状況（前の車との距離 m、自車の速度 km/h）を与えると、搭載している機能の動作結果を表示する |
| 出力の例 | `スタンダード 距離15m 速度40km/h → 自動ブレーキ作動 ／ 速度を35km/hに調整` |
| 未適用 | 機能の組み合わせごとに、継承でサブクラスを作る（継承の乱用） |
| 適切 | 運転支援機能をそれぞれ部品のクラスにし、車は部品の一覧を持って処理を任せる（委譲） |
| 過剰適用 | なし |
| 変更要求1 | `composition.lane-keep`: 新機能「車線維持支援」を追加し、3つの機能すべてを持つグレード「プレミアム」を作る。期待: 適切のほうが少ない |
| 変更要求2 | `composition.brake-distance`: 衝突被害軽減ブレーキが作動する距離を変える。期待: 少なくならない（どちらも1か所） |
| 実装課題の追加仕様 | スタンダードからアダプティブクルーズコントロールを外し、代わりに駐車支援を付ける |
| 自己チェック | ① 機能ごとに部品のクラスを作った ② 車は部品を持って処理を任せている（機能を足すために継承していない） ③ 機能の組み合わせを変えるのに、新しい車のクラスが要らない |
| 言語ごとの注意 | C++: 部品は静的に確保し、車はポインタの固定長配列で持つ。VBA: 継承がないため、未適用は「組み合わせごとに、機能の処理をコピーしたクラスを作る」で表す（組み合わせの数だけクラスが増えるという同じ問題を示す。§4 K22-3） |

## 4. Claude が独自に置いた前提（2026-10-16 確認済み・すべて提案どおり）

DES-01 §14 の K22 の内訳。

| # | Claude の前提 | 他の選択肢 |
