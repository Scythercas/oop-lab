## 0. この文書の位置づけ

「必ず実装して」の指示を受けてから、**何を、どの順番で作り、どこで区切るか**を決める。期限は設けない（REQ-02 CON-05）ので、日付ではなく、段階（マイルストーン）と、各段階の完了条件で進み具合を管理する。

本書は 2026-10-19 にユーザが確認し、確定した。

## 1. 進め方の原則

| 原則 | 内容 | 理由 |
| --- | --- | --- |
| 不確実なものを先に確かめる | 最初に、詳細設計書 §12 の T1〜T9 を試作で確かめる | だめだったときの代わりの手段に、早く切り替えるため。後で分かると作り直しが大きい |
| 早く一通り動かす | 1つの概念を3言語で、「教材 → 自動確認 → ビルド → 公開」まで先に通す（縦切り） | 仕組みの穴を、教材を量産する前に見つけるため |
| 自動確認を先に作る | 教材の検証・コードの実行確認・VBA 確認ツールを、教材を量産する前に完成させる | 約153個のコードの状態を、手作業で確かめずに済むようにするため |
| 教材の書き方を最初の1概念で固める | 最初の概念をユーザにレビューしてもらい、その結果を「教材の執筆・レビュー要領」に反映してから残りを作る | 同じ指摘を6回繰り返さないため |
| main をいつも公開できる状態に保つ | 作業はブランチで行い、Pull Request で main にマージする（`git-branch-workflow`） | どの時点でも、公開中のサイトが壊れないようにするため |
| 設計とずれたら、設計書を先に直す | 実装中に設計の変更が必要になったら、先に設計書を直し（大きな判断は ADR）、根幹に関わるならユーザに確認してから実装する（K40） | 設計書とコードの食い違いを残さないため |

| 段階 | 目的 | 完了条件 |
| --- | --- | --- |
| M0 技術の確認 | T1〜T9 を確かめ、設計の前提が成り立つか決着させる | T1〜T9 の結果を記録し、だめだったものは代わりの手段に切り替えて設計書に反映した |

## 3. 各段階の作業

作業は「作業単位（WP）」に分け、原則として1つの作業単位を1つのブランチと Pull Request にする。

### 3.1 M0 技術の確認

| WP | 内容 | ブランチ | 成果物 |
| --- | --- | --- | --- |
| WP0-1 | T1〜T9 の試作。試作のコードは使い捨てで、main にはマージしない | `chore/spike-tech-checks`（マージしない） | 結果の記録（詳細設計書 §12 に追記する Pull Request） |

確かめる順番は、だめだったときの影響が大きいものからにする。

| 順番 | 事項 | だめだった場合の影響 |
| --- | --- | --- |
| 1 | T2・T3（VBA のコンパイルと、実行時エラーの扱い） | 確定済みの決定（DQ2）の変更になり、ユーザへの相談が要る |
| 2 | T1・T9（Cloudflare の配信設定とプレビュー、Astro と CSP） | 配信の構成とセキュリティの設計が変わる |
| 3 | T5・T6（C++ の出力とメモリ確保の検出、Java の文字コード） | 教材の書き方の決まりが変わる |
| 4 | T4・T7（VBA の色付け、料金の数値） | 影響は小さい |
| 5 | T8（Web フォントを含めた表示速度） | ある程度できたサイトでないと測れないため、M2 の終わりに確かめる |

### 3.4 M3 教材の量産

1つの概念を1つの Pull Request にし、それぞれユーザのレビュー（U4）を経てマージする。順番は、作るのが難しく、仕組みの穴が見つかりやすいものからにする（K41）。

| 順番 | 概念 | 先に作る理由 | ブランチ |
| --- | --- | --- | --- |
| 1 | 継承 | VBA で代わりの書き方（委譲と `Implements`）と注記（FR-013）が必要で、最も難しい | `feature/content-inheritance` |
| 2 | ポリモーフィズム | C++ の仮想関数と、静的に確保したオブジェクトの扱いを確かめる | `feature/content-polymorphism` |
| 3 | 抽象化 | ポリモーフィズムとの違いを、解説で書き分ける必要がある | `feature/content-abstraction` |
| 4 | クラスとインスタンス | 過剰適用（輪ごとに別のクラス）を3言語で作る | `feature/content-class-instance` |
| 5 | コンポジションと委譲 | VBA の未適用（組み合わせごとのクラス）が代わりの書き方になる | `feature/content-composition` |

## 5. 作業単位ごとの完了の定義

すべての作業単位で、次を満たしてから main にマージする。

- CI のすべてのジョブが成功している。
- テスト計画書（TST-01）でその作業単位に対応するテストを追加し、成功している。
- 設計から変えた点があれば、設計書（必要なら ADR）を先に直している（K40）。
- `docs/README.md` の進み具合の表を更新している。
- Pull Request の説明に、何を作ったか、どのテストで確かめたか、ユーザに見てほしい点を書いている。

マージは、通常のマージ（merge commit）で行う。教材の Pull Request はユーザがマージする（TST-01 K35）。コードの Pull Request は、CI が成功したら Claude がマージし、段階の終わりにまとめて報告する（K38）。設計書だけの Pull Request は、根幹に関わる変更（K40）ならユーザの確認を経てから、それ以外（記録の追記や表記の修正）なら Claude がマージする。

## 6. 進み具合の管理

- 段階を GitHub のマイルストーン、作業単位を Issue にして管理する（K39）。Issue と Pull Request を結びつけ、マージで Issue を閉じる。
- 作業がセッションをまたいでも引き継げるように、段階の終わりごとに `docs/README.md` の表を更新する。

| # | リスク | 対策 |
| --- | --- | --- |
| R1 | VBA のコンパイルを外から確かめられない（T2） | M0 の最初に確かめる。だめなら、DQ2 の変更をユーザに相談する |

## 8. 作業の決まり

| 項目 | 決まり |
| --- | --- |
| ブランチ名 | `<種別>/<内容>`（`feature/`・`fix/`・`chore/`・`docs/`・`test/` など。`git-branch-workflow` に従う） |
| コミットメッセージ | 日本語で、先頭に種別（`feat:`・`fix:`・`chore:`・`docs:`・`test:`）を付ける。末尾に Claude との共同作業の記載を付ける |
| 依存ライブラリ | 版を固定する（DES-03 §2.4）。追加するときは、用途とライセンスを Pull Request に書く |
| 不具合 | GitHub Issues に記録し、再現するテストを先に書いてから直す（TST-01 K32） |
