## 0. この文書の位置づけ

教材（`content/`）を書く人（初回は Claude）と、レビューする人（ユーザ）のための手引きです。DES-02 が「何を作るか」を決めるのに対し、この文書は「どう書くか」「どう確かめるか」を決めます。最初の概念のレビューで出た指摘は、ここに書き足して、残りの概念に生かします（実装計画書 §2）。

---

## 1. 書く手順

1. DES-02 §2 の、その概念の仕様（題材・設計・変更要求・課題・自己チェック）を読む。
2. 期待する実行結果（`expected-output.txt`）を先に決める。初期状態・変更要求ごと・模範解答の出力を、1文字の違いもなく3言語でそろえる。
3. 「未適用」「適切」「過剰適用」の順にコードを書く。1言語を書き上げてから、残りの言語に移す（§3.2 の直訳調にしない注意を守る）。
4. 変更要求の状態は、設計の状態に「開発者が自然に行う最小の編集」を当てて作る。編集の量が、そのまま画面の修正量になるため、余計な整形や名前の変更を混ぜない。
5. 解説・設計の解説・変更要求の解説・クイズ・言語ごとの補足を書く。
6. §5 の手順で確かめてから、Pull Request を作る。

`concept.yaml` の `related` には、すでにある概念だけを書ける（V03）。関連する概念が後からできたら、そのときに足す（M3 で、カプセル化の `related` にクラスとインスタンス・抽象化を足す）。

## 2. 文章の書き方

| 項目 | 決まり | 例 |
| --- | --- | --- |
| 文体 | です・ます調。1文を短くする | 「規則が1か所にまとまります。」 |
| 専門用語 | 初出で説明する（CR-12）。オブジェクト指向の用語も、車載の用語も同じ | 「変速機（トランスミッション。エンジンの回転を車輪に伝える装置）」 |
| 簡略化の明示 | 題材の仕様の最後に「※ 実際の車の仕組みを、学習用に簡略化したモデルです。」を書く（CR-14） | — |
| 固有名詞 | 実在のメーカー名・製品名・公開されていない仕様を書かない（CR-14） | — |
| 表記 | 括弧・句読点は全角。英数字と記号（`→` など）は半角。コード中の名前は `` `shiftTo` `` のようにコードとして書く | 「`shiftTo`（言語によって名前が違います）」 |
| 言語の違い | 名前が言語ごとに違うものを文章で指すときは、代表の名前に「（言語によって名前が違います）」を添えるか、言語を問わない言い方（「切り替えの入口」）にする | — |
| 見出し | 解説は FR-020 の8つの見出し（`##`）だけを使い、ページの見出し（`#`）は書かない（画面が概念名を出すため） | — |
| 主張の強さ | 解説の断言は、教材のコードが実際に保証していることにとどめる。簡単にするために省いた確かめは、仕様に明記する | 「不正な状態にならない」ではなく「呼び出す側の確かめ忘れが起きない」 |
| 用語の統一 | 同じものを同じ言葉で呼ぶ。設計によって役割が変わる場合は、その設計に合う言葉を使う | 適切な設計では「呼び出す側」、未適用では「書き換える側」 |

## 3. コードの書き方

### 3.1 全言語に共通

- DES-02 §1.2・§1.3 の決まり（入力なし、整数だけを出力、規模の目安、言語ごとの決まり）に従う。
- 出力の形は、概念の中で1つに決め、仕様の「表示の例」に書く。例（カプセル化）: `D→R 20km/h 拒否 現在D`。
- コメントは、クラスの役割を1行と、規則の意味（「走行中は R に入れない」など）にだけ書く。変更要求で規則が変わるときは、コメントも一緒に直す（差分に現れて、何が変わったかが読み取れる）。
- 3つの設計で、規則と関係のない部分（クラスの役割、出力の処理、`main` の流れ）はできるだけ同じにする。設計の違いだけが差分に出るようにするためである。
- 変更要求の状態では、ファイル名と行の並びを、設計の状態から必要以上に動かさない。

### 3.2 直訳調にしない（CR-08）

| 言語 | カプセル化での例 |
| --- | --- |
| Java | 1クラス1ファイル。値を読むメソッドは `getPosition`、規則つきの操作は `shiftTo`。真偽値の戻り値で受け付け／拒否を返す |
| C++ | 関数とファイルは snake_case（`shift_to`、`park_button.h`）。メンバ変数は末尾に `_`。読むだけの関数は `position() const`。データだけの型は `struct`。関数の本体の `{` は次の行 |
| VBA | 非公開の変数は `m` で始める（`mPosition`）。読むだけなら `Property Get`、規則つきの操作は結果を返すため `Function`。大文字と小文字を区別しないので、変数名をクラス名と重ねない（`Transmission` の変数は `gearbox`） |

### 3.3 クイズのコード

- 3言語分を用意し、それぞれ単体でコンパイルできる形にする（Java は1クラス、C++ はインクルードガード付きのヘッダ、VBA は1つのモジュール）。
- C++ の禁止事項（`new`、`std::string` などのコンテナ、例外）はクイズのコードにも当てはまる（V09）。

## 4. 各ファイルの中身

### 4.1 解説（`explanation.md`）

| 見出し | 書くこと |
| --- | --- |
| 定義 | 1〜2文の定義と、この教材の題材では何に当たるか |
| 目的 | 何を防ぐ・何をしやすくするか |
| メリット | 箇条書き。太字の見出し語と、題材に即した説明 |
| デメリット | 箇条書き。2つ目の変更要求で見せる弱点を必ず含める |
| 使い時 | 判断の目安になる条件。車載の場面の例を添える |
| 使わない方がよい時 | 条件と例。迷ったときの目安も書く |
| よくある誤り | 過剰適用・誤用。設計比較の「過剰適用」と対応させる |
| 関連概念 | 関係の説明だけを書く（リンクは `related` から画面が作る） |

### 4.2 設計の解説（`variations/*/commentary.md`）

「良い点」「問題点」の見出しで書く（V11）。未適用にも良い点（短い、すぐ書ける など）を書き、適切にも問題点（コードが増える など）を書く。どの設計にも理由があることを示すためである。

### 4.3 変更要求（`changes/*/change.yaml`）

| 項目 | 書くこと |
| --- | --- |
| `title` | 要求を1行で |
| `description` | 要求の背景（なぜ必要か）と、何をどう変えるか |
| `commentary.reason` | 修正量の差がどこから来たか。直したファイルの名前を挙げる |
| `commentary.missRisk` | 修正漏れが起きやすい箇所と、漏れると何が起きるか |
| `commentary.lesson` | この変更から分かる、概念の使いどころ |

2件目（適切でも修正量が減らない例）では、その要求が設計の弱点を突いていることと、要求そのものの是非も解説する（DES-02 §4 K22-2）。

### 4.4 クイズ（`quiz/*.yaml`）

- 内訳は DES-02 §1.4 のとおり。設問は「最も適切なものはどれですか」のように、答えが1つに決まる問い方にする。
- 正解の記号（a〜d）は、10問の中で偏らないように散らす。
- 誤りの選択肢は、ありがちな誤解に基づかせる。明らかにふざけた選択肢は作らない。
- 選択肢の場面には、判断に必要な条件（規則があるか、変える箇所がいくつか など）を書き切る。条件が欠けると、正解が2つに読める。
- 設問の文に、解説で否定している考え方を前提として書かない（例: カプセル化を「取得・設定のメソッドを用意すること」と言い換えない）。
- 別の設問の選択肢や解説の例文と、ほぼ同じ文を正解にしない（1問を解くと別の問の答えが分かってしまう）。
- 解説（`explanation`）は正解の理由を、`wrongReasons` は誤りの選択肢ごとの理由を書く。

### 4.5 実装課題（`exercises/*/exercise.yaml`）

- 課題文は「何を書き直すか」と「何を満たせばよいか」。追加の仕様には、理由（なぜその規則が要るか）と、表示の変わり方の例を書く。
- 自己チェック項目は、学習者が自分のコードを見て「できた／できなかった」を判断できる文にする。

### 4.6 言語ごとの補足（`notes/*.md`）

その言語での書き方の違いと理由を、3〜4項目の箇条書きで書く。その言語で概念を直接表現できないときは、見出し部の `unsupported` に注記を書く（CR-11）。

## 5. 確かめる手順

| 順 | コマンド | 確かめること |
| --- | --- | --- |
| 1 | `npm run content:check` | 形式・件数・書式・禁止事項（V01〜V11）。最後に件数の一覧が出る |
| 2 | `npm run build` | 変更要求の期待と修正行数の照合（B01） |
| 3 | `node tools/ci/run-code-checks.ts --lang cpp`（手元に g++ がある場合） | C++ のビルド・実行・出力の照合。Java は CI で確かめる |
| 4 | `npm run vba:verify`（Excel のある Windows の PC） | VBA の実行・出力の照合と、確認記録の更新。終了後に AccessVBOM が 0 に戻ったことを確かめる |
| 5 | `npm run vba:check` | 確認記録が今の教材と一致するか |
| 6 | Pull Request のプレビュー URL | 画面での見え方（差分が意図した編集になっているか、修正量の棒、解説） |

VBA の確認記録はハッシュ値で教材と結び付いているため、VBA のコードか期待結果を直したら、手順4をやり直す。

## 6. レビューの観点（ユーザ向け）

Pull Request とプレビュー URL で、次を見てください。気になる点は、Pull Request のコメントで指摘してください。書き方の好みも歓迎します（この文書に反映します）。

| 観点 | 見るところ | 根拠 |
| --- | --- | --- |
| 題材 | 車載の題材として不自然でないか。簡略化しすぎて誤解を招かないか | CR-02、CR-14 |
| 分かりやすさ | 解説が初学者に通じるか。専門用語が初出で説明されているか | CR-03、CR-12 |
| 設計の対比 | 未適用・適切・過剰適用の違いが、設計比較の差分で読み取れるか | CR-04 |
| 変更の説得力 | 変更シミュレーションの修正量の差に納得できるか。2件目の弱点の説明は公平か | CR-05 |
| クイズ | 正解が1つに決まるか。解説と誤答の理由に納得できるか | CR-06 |
| 課題 | 課題文と自己チェックで、何をすればよいか分かるか | CR-07 |
| コード | 各言語の書き方として自然か（直訳調でないか）。C++ が車載組込みらしい書き方か | CR-08、CR-15 |
| 言語ごとの補足 | 言語の違いの説明が正しく、役に立つか | FR-022 |
