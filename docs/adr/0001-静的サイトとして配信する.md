# ADR-0001: 初回は静的サイトとして配信し、将来のサーバ機能は同じドメインの API として追加する

- 日付: 2026-10-16
- ステータス: 採用（2026-10-16）

## 文脈

- 初回リリースの運用費は月額0円（REQ-02 NFR-01）。ログインはなく、学習データはブラウザ内だけに保存する（REQ-02 §8.2）。
- 実装課題は自己評価だけで、学習者のコードを実行・送信しない（REQ-02 FR-069）。
- 将来、ログイン・採点・ランキングを追加する。その時点の費用上限は月額5,000円（REQ-02 RQ12, NFR-15）。

初回に実行時のサーバ処理が要るかを決める必要があった。

## 検討した選択肢

### 案A: 静的サイト（ビルド時に全ページを生成）。将来の機能は API として後から足す

- 利点: 運用費0円で済む。障害点が少ない。表示が速い。セキュリティ上の攻撃面が小さい
- 欠点: 将来の機能を足すときに、API とデータベースを新たに用意する必要がある

### 案B: 最初からサーバ（サーバレス関数など）でページを生成する

- 利点: 将来の機能を足すときに、同じ仕組みの中で済む
- 欠点: 初回には使わない仕組みを運用することになる。無料枠の制限を気にする必要が出る

## 決定

案A を採用する。将来の API は、同じドメインの `/api/*` として追加する（CORS の設定が不要になる）。

## 理由

初回の要件には、実行時にサーバで処理するものが1つもない。将来の機能は時期も方式（採点・ランキングの基準）も未定なので、今サーバを用意しても形が合わない可能性が高い。代わりに、追加時に作り直しが起きないよう、学習データの読み書きとクイズの判定を1か所にまとめておく（DES-01 §1.4）。

## 結果と影響

- 得られること: 運用費0円、単純な運用、速い表示
- 諦めること: 端末間での学習データの引き継ぎ、ランキングの公平性（初回は正解がブラウザから見える）
- 見直す条件: ログイン・採点・ランキングのいずれかに着手するとき
