# ADR-0003: フロントエンドに Astro・React・TypeScript を使う

- 日付: 2026-10-16
- ステータス: 採用（2026-10-16）

## 文脈

- サイトの大部分は教材（解説・コード・差分）で、ビルド時に作れる。
- 対話が必要な部分は、表示言語の切り替え、設計の切り替え、変更要求の選択、クイズ、実装課題のエディタ、進捗表示、学習データの管理に限られる。
- 初回表示は3秒以内（REQ-02 NFR-05）。教材の追加はファイルの追加だけで済ませたい（NFR-09）。
- 実装と保守は主に Claude が行う。

## 検討した選択肢

### 案A: Astro（静的サイト生成）＋ React（対話部品だけ）＋ TypeScript

- 利点: ページごとに HTML を生成し、JavaScript は対話部品の分だけ配る。教材データの形式を検証する仕組みがある。JavaScript が動かなくても解説は読める
- 欠点: Astro と React の2つの仕組みを理解する必要がある

### 案B: React だけの1ページアプリ（Vite で構築）

- 利点: 仕組みが1つで単純
- 欠点: 最初に読み込む量が増える。教材をすべて JavaScript で扱うことになり、ページごとの最適化や検索エンジン対応に手間がかかる

### 案C: Next.js の静的出力

- 利点: 利用者が多い
- 欠点: 静的サイトには使わない機能が多く、重い

### 案D: フレームワークを使わない TypeScript

- 利点: 最も軽い
- 欠点: 差分表示・クイズ・エディタの状態管理を自前で書くことになり、保守しにくい

## 決定

案A を採用する。対話部品には React を使う。

## 理由

教材中心のサイトに対して、表示の速さ・教材データの検証・保守のしやすさの釣り合いが最もよい。React は利用者が多く、将来のログイン画面などでも部品を探しやすい。

## 結果と影響

- 得られること: 速い表示、教材データの型検証、JavaScript が動かない環境でも解説が読めること
- 諦めること: 仕組みの単純さ（Astro と React の2層になる）
- 見直す条件: 対話部分が大半を占めるようになり、ページ単位の生成の利点が薄れたとき
