# ADR-0004: 教材はリポジトリ内のファイルで管理し、差分と修正量はビルド時に計算する

- 日付: 2026-10-16
- ステータス: 採用（2026-10-16）

## 文脈

- 教材コードは「そのまま動く実際のコード」で、Java・C++ は自動で実行確認する（REQ-02 CR-09, NFR-10）。
- 教材は Claude が下書きし、ユーザがレビューする（CR-13）。履歴を残したい（REQ-02 §8.1）。
- 画面に表示する差分と修正量が食い違ってはならない（NFR-12）。変更要求ごとに「適切な設計のほうが修正量が少ない」などの期待がある（CR-05）。
- 運用費は月額0円。

## 検討した選択肢

### 教材の置き場所

- 案A: リポジトリ内のファイル（YAML・Markdown・各言語のソースファイル）
  - 利点: 版管理で履歴が残る。Pull Request でレビューできる。ソースファイルをそのままコンパイル・実行できる。費用がかからない
  - 欠点: 教材を書くのにファイル構成の知識が要る（主に Claude が書くので問題は小さい）
- 案B: ヘッドレス CMS（教材管理用の外部サービス）
  - 利点: 画面から教材を編集できる
  - 欠点: 外部サービスへの依存と費用。ソースコードの実行確認と結びつけにくい
- 案C: データベース
  - 欠点: 初回はサーバを持たない（ADR-0001）ので合わない

### 差分の計算のタイミング

- 案X: ビルド時に計算し、結果をページに埋め込む
  - 利点: 実行時の処理と JavaScript が減る。修正量の期待との照合をビルド時にでき、不正な教材を公開前に止められる
  - 欠点: 学習者のコードと模範解答の差分（FR-068、Could）には使えない
- 案Y: ブラウザで表示のたびに計算する
  - 利点: 仕組みが単純
  - 欠点: 期待との照合が公開後にしかできない

## 決定

教材は案A、差分は案X を採用する。変更後のコードは「差分」ではなく「変更後の完全なソース」として置き、差分はビルド時に計算する。

## 理由

教材コードを実際に実行して確かめられることが、このアプリの品質の土台になる。完全なソースとして置けば、変更後の状態もそのまま実行確認できる。差分と修正量を同じ計算から出すことで NFR-12 を満たし、期待との照合で CR-05 を公開前に確認できる。

## 結果と影響

- 得られること: 教材の履歴とレビュー、実行確認、差分と修正量の一致、期待の自動照合
- 諦めること: 画面からの教材編集（運営者は Claude とユーザだけなので不要）
- 見直す条件: FR-068（学習者のコードとの差分）を実装するときは、その部分だけブラウザでの計算を足す
