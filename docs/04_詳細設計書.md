## 2. モジュール設計

### 2.1 依存の向き

```text
 pages（Astro） ──▶ components（React） ──▶ domain
      │
      └──▶ build ──▶ content
 tools/ci ──▶ content

 ・domain は、他のどのモジュールにも依存しない
 ・build と content はビルド時だけ動き、ブラウザには配られない
```

- 画面の部品（components）は localStorage に直接触れず、domain の `LearningStore` を通す（NFR-15 ①）。
- domain が使うブラウザの保存領域は、引数で受け取る（単体テストで偽物に差し替えるため）。
- 教材の型（`src/content/schema.ts`）は、build・pages・tools/ci で共有する。
- `localStorage` を学習データストア（`src/domain/learning-store.ts`）以外で使っていないことを、静的検査（ESLint の規則）で CI が確かめる（NFR-15 ①を守り続けるため）。ただし、表示言語を決める先頭のスクリプト（§5.4）だけは、描画の前に動く必要があるため、localStorage を読み取り専用で直接読む。このスクリプトは学習データストアの定数（キー名・項目の場所・既定の言語）からビルド時に生成し、ESLint の規則の例外として明示する。

### 2.3 将来差し替える2つの境界

将来のログイン・ランキングに備えて、次の2つだけを型（インタフェース）として切り出す（DES-01 §13）。

```ts
/** 学習データの読み書き。画面の部品はこれだけを使う */
interface LearningStore {
  readonly status: StoreStatus;                           // 保存できる状態か（§6.4）
  get(): Readonly<LearningData>;                          // 現在の学習データ
  update(change: (data: LearningData) => void): SaveResult; // 最新を読み直して変更し、保存する（§6.3）
  clear(): SaveResult;                                    // すべて消す
  subscribe(listener: (data: Readonly<LearningData>) => void): () => void; // 自分や他のタブでの変更の通知
  exportJson(): string;                                   // 書き出し（FR-073）
  importJson(text: string): ImportResult;                 // 読み込み（FR-073）
}
type StoreStatus = "ok" | "unavailable" | "newer-version";
type SaveResult = { ok: true } | { ok: false; reason: "unavailable" | "quota-exceeded" | "newer-version" };

/** クイズの判定。将来はサーバ側の判定に差し替える（NFR-15 ③）。正解データを取得できないときは QuizJudgeError で reject する */
interface QuizJudge {
  judge(questionId: string, choiceId: string): Promise<JudgeResult>;
}
type JudgeResult = {
  correct: boolean;
  correctChoiceId: string;
  explanation: string;                      // 正解の理由
  wrongReasons: Record<string, string>;     // 正解以外の選択肢ごとの、誤りである理由
};
```

- `QuizJudge` は、初回から非同期（`Promise`）にする。初回の実装は正解データのファイルを取得して照合するだけだが、将来サーバに問い合わせる形に替えても、呼び出し側を変えずに済む。
- `LearningStore` は同期のままにする。将来ログインを足しても、ブラウザ内の学習データを正とし、サーバとの同期は別の仕組みとして追加するため（ADR-0006、K23）。これは DES-01 §1.4 の「学習データストアの保存先をサーバに切り替える」を具体化したもので、NFR-15 ①は「画面の部品と学習データストアの使い方を変えずに、サーバ側の機能を足せる」ことで満たす（K23 でユーザ確認済み）。

## 3. 教材ファイルの定義

### 3.1 全ファイル共通の書式

- 文字コードは UTF-8（BOM なし）、改行は LF、ファイルの末尾に改行を1つ置く。
- 行末に空白を置かない。字下げは空白4つで、タブは使わない。
- Markdown の中に HTML を書かない（書いても文字として表示される。DES-01 §8）。
- `.gitattributes` に `* text=auto eol=lf` を書き、Windows で取り出しても改行が LF のままになるようにする。

### 3.2 `languages.yaml`

| 項目 | 内容 |
| --- | --- |
| `id` | 言語 ID（`java` ／ `cpp` ／ `vba`）。フォルダ名に使う |
| `label` | 画面に出す名前 |
| `order` | 表示言語の切り替えでの並び順 |
| `highlight` | Shiki の言語指定 |
| `editor` | エディタ（CodeMirror）の言語指定 |
| `extensions` | ソースファイルの拡張子 |
| `classCount` | クラス数の数え方。`pattern`（その正規表現に一致する行の数）か `fileExtension`（その拡張子のファイルの数）（§4.5） |
| `check` | 動作確認の方法。`ci`（§8）か `vba-tool`（§7） |
| `commands` | `check: ci` のときの、ビルド・実行・文法確認のコマンド。`{out}`（出力先）・`{sources}`（ビルド対象）・`{files}`（全ファイル）を置き換えて使う |
| `forbiddenPatterns` | ソースに書いてはいけないものの正規表現（C++ の動的メモリ確保など。§8.2） |

**初回の内容（抜粋）**

```yaml
- id: java
  label: Java
  order: 1
  highlight: java
  editor: java
  extensions: [".java"]
  classCount: { pattern: '^\s*(public\s+|abstract\s+|final\s+)*(class|interface|enum)\s+\w+' }
  check: ci
  commands:
    build: javac -encoding UTF-8 -d {out} {files}
    run: java -Dstdout.encoding=UTF-8 -cp {out} Main
    syntaxCheck: javac -encoding UTF-8 -d {out} {files}

- id: cpp
  label: C++
  order: 2
  highlight: cpp
  editor: cpp
  extensions: [".h", ".cpp"]
  classCount: { pattern: '^\s*(class|struct)\s+\w+[^;]*$' }
  check: ci
  commands:
    build: g++ -std=c++17 -Wall -Wextra -Werror -pedantic -fno-exceptions -fno-rtti -o {out}/main {sources} tools/ci/alloc_guard.cpp
    run: "{out}/main"
    syntaxCheck: g++ -std=c++17 -Wall -Wextra -Werror -pedantic -fno-exceptions -fno-rtti -fsyntax-only {files}
  forbiddenPatterns:
    - '\bnew\b'
    - '\bdelete\s*(\[\s*\])?\s*[A-Za-z_(]'     # delete 式（関数の削除指定 "= delete;" は許す）
    - '\b(malloc|calloc|realloc|free)\s*\('
    - 'std::(vector|string|map|unordered_map|list|deque|set|function|unique_ptr|shared_ptr|make_unique|make_shared)\b'
    - '\b(try|catch|throw)\b'

- id: vba
  label: VBA
  order: 3
  highlight: vb
  editor: vb
  extensions: [".bas", ".cls"]
  classCount: { fileExtension: ".cls" }
  check: vba-tool
```

### 3.3 概念フォルダ内のファイル

#### `concept.yaml`

| 項目 | 形 | 必須 | 内容 |
| --- | --- | --- | --- |
| `id` | 文字列 | ○ | 概念 ID。フォルダ名と同じ |
| `order` | 整数 | ○ | 推奨学習順（1から、重複なし） |
| `title` | 文字列 | ○ | 概念の名前 |
| `theme` | 文字列 | ○ | 題材の名前 |
| `summary` | 文字列 | ○ | トップ画面に出す一言（40字以内） |
| `spec` | Markdown | ○ | 題材の仕様 |
| `related` | 概念 ID の配列 | ○ | 関連概念 |
| `variations` | 設計の配列 | ○ | 用意する設計。`unapplied` と `proper` を必ず含む |

#### `explanation.md`

見出し（`##`）が「定義」「目的」「メリット」「デメリット」「使い時」「使わない方がよい時」「よくある誤り」「関連概念」の8つで、この順に過不足なく並ぶ（FR-020）。「関連概念」の節には関係の説明を書く。関連概念のページへのリンクは `concept.yaml` の `related` から自動で作り、この節の後ろに並べる（FR-021）。

#### `notes/{言語}.md`（任意）

| 部分 | 内容 |
| --- | --- |
| 見出し部の `unsupported`（任意） | その言語では概念を直接表現できない旨と理由。設計比較と変更シミュレーションのコードの上に出す（FR-013） |
| 本文 | 言語ごとの補足。解説の画面に出す（FR-022） |

見出し部は、ファイルの先頭に `---` で囲んだ YAML で書く。

```markdown
---
unsupported: VBA には継承がないため、共通の処理を部品のクラスに任せ（委譲）、共通の型は Implements で表しています。
---
（本文: VBA での補足）
```

#### `variations/{設計}/commentary.md`

その設計の良い点・問題点。見出し「良い点」「問題点」のどちらか一方以上を持つ（FR-036。V11 で検証する）。

| `title` | 文字列 | ○ | 変更要求の見出し |
| `description` | Markdown | ○ | 変更要求の説明 |
| `expectation` | `proper-fewer` ／ `proper-not-fewer` | ○ | 修正行数の期待（§4.4） |

| `commentary.missRisk` | Markdown | ○ | 修正漏れが起きやすい箇所（FR-043） |

#### `quiz/questions.yaml`（設問の配列。正解は含めない）

| 項目 | 形 | 必須 | 内容 |
| --- | --- | --- | --- |
| `id` | `概念ID.qNN` | ○ | 設問 ID |

| 項目 | 形 | 必須 | 内容 |
| --- | --- | --- | --- |
| `questionId` | 設問 ID | ○ | 対応する設問 |
| `correct` | `a`〜`d` | ○ | 正解 |
| `explanation` | Markdown | ○ | 正解の理由 |
| `wrongReasons` | 選択肢 ID → Markdown | ○ | 正解以外の3つの選択肢それぞれが誤りである理由 |

#### `exercises/{名前}/exercise.yaml`（名前は課題 ID の「.」より後ろ。例: `ex01`）

| 項目 | 形 | 必須 | 内容 |
| --- | --- | --- | --- |
| `id` | `概念ID.exNN` | ○ | 課題 ID |
| `statement` | Markdown | ○ | 課題文 |
| `additionalSpec` | Markdown | ○ | 課題専用の追加仕様（DES-01 K20） |
| `checks` | 3つ以上 | ○ | 自己チェック項目。各項目は `id`（`課題ID.cN`）と `text` |

課題ごとのフォルダには、`exercise.yaml` のほかに `expected-output.txt` と `answer/{言語}/`（模範解答）を置く。課題を増やすときはフォルダを足すだけで済む（NFR-09）。DES-01 §4.1 の `exercise/` を、複数の課題を置ける形に具体化した。初回は1概念1課題とする。

#### ソースファイルと期待結果

| 言語 | 決まり |
| --- | --- |
| Java | 1クラス1ファイル。入口は `Main.java` の `main` |
| C++ | クラスごとに `.h` を1つ。入口は `main.cpp`（ビルド対象 `{sources}` は `.cpp` だけ） |
| VBA | 標準モジュールは `.bas`、クラスモジュールは `.cls`。ファイル名＝モジュール名。入口は `Program.bas` の `Sub Main()`。取り込み用の見出し行（`VERSION 1.0 CLASS` や `Attribute VB_Name`）は書かない（確認ツールが付ける。§7.3） |

`expected-output.txt` には標準出力の内容をそのまま書く（§3.1 の書式に従う）。

## 4. 差分と修正量

### 4.1 用語

「状態」は、1つの設計（または変更後の状態・模範解答）の、1言語分のソースファイル一式を指す。

### 4.2 ファイルの対応づけ

同じ言語の2つの状態の間で、相対パスが同じファイルを対応づける。片方にしかないファイルは「追加」または「削除」とする。

### 4.3 行の差分

行単位の差分ライブラリ（jsdiff の行差分）で計算する。書式は §3.1 でそろっているため、空白や改行の正規化はしない。

### 4.4 修正量の定義と期待の照合

| 数値 | 定義 |
| --- | --- |
| 変更ファイル数 | 追加・削除・変更されたファイルの数 |
| 変更箇所数 | 変わった行が連続しているかたまりの数。削除と追加が隣り合っていれば1つと数える。追加・削除されたファイルは、1ファイルを1箇所と数える |
| 追加行数・削除行数 | 空行も含めて数える（差分表示と一致させるため。NFR-12） |
| 修正行数 | 追加行数＋削除行数 |

期待の照合（ビルド時の検証 B01）は、すべての表示言語で次が成り立つことを確かめる。過剰適用は照合しない（解説で扱う）。

| `expectation` | 条件 |
| --- | --- |
| `proper-fewer` | 適切の修正行数 ＜ 未適用の修正行数 |
| `proper-not-fewer` | 適切の修正行数 ≧ 未適用の修正行数 |

### 4.5 規模（FR-035）

| 数値 | 定義 |
| --- | --- |
| ファイル数 | 状態に含まれるソースファイルの数 |
| クラス数 | `languages.yaml` の `classCount` に従って数える（VBA はクラスモジュールの数） |
| 行数 | 空行を除いた行の数 |

### 4.6 左右に並べる表示の行のそろえ方

変わらない行は左右の同じ高さに置く。変わったかたまりの中では、削除された行を左、追加された行を右に上から並べ、行数が少ない側に空の行を足して高さをそろえる。

## 5. 画面の内部設計

### 5.1 ページの生成

- DES-01 §3.1 の URL ごとに、Astro が静的なページを生成する（概念 × 5つのタブ）。
- 存在しない URL には「ページが見つかりません」のページを返す。

### 5.2 ページに埋め込むデータ

画面ごとに必要なデータをビルド時に組み立て、ページの中に JSON として埋め込む。3言語分をすべて含めるため、表示言語の切り替えでは通信しない（NFR-05）。

| 画面 | 埋め込むデータ |
| --- | --- |
| 設計比較 | 言語ごとに、各設計のファイル（色付け済みの行）と規模、設計の組み合わせごとの差分と修正量、`unsupported` の注記 |
| 変更シミュレーション | 変更要求ごと × 言語ごと × 設計ごとに、変更前後の差分と修正量、解説 |
| クイズ | 設問と選択肢（言語ごとのコードを含む）。**正解は含めない** |
| 実装課題 | 課題ごとに、課題文・追加仕様・自己チェック項目、言語ごとの開始コード（エディタ用に1つの文字列にまとめたもの。§5.6）と模範解答（ファイルごとに色付け済み） |

- 正解データは、概念ごとに `/data/answers/{概念ID}.json` として配信し、クイズで最初に解答したときに取得する（DES-01 §3.9）。
- 正解データの形は、設問 ID ごとに `correct`（選択肢 ID）・`explanationHtml`（正解の理由）・`wrongReasonsHtml`（選択肢 ID → 誤りである理由）とする。Markdown はビルド時に HTML にし、Markdown の中の HTML は文字としてエスケープする（DES-01 §8）。
- 1ページあたりのデータ量の見込みは、圧縮後で数十〜百数十 KB（3言語 × 状態約9 × 1状態あたり最大200行）。

### 5.3 対話部品

| 部品 | 置く画面 | 役割 | 持つ状態 |
| --- | --- | --- | --- |
| `LanguageSwitcher` | 全画面のヘッダ | 表示言語の切り替え | なし（`LearningStore` の値を使う） |
| `StorageNotice` | 全画面の上部 | 保存できないときなどの帯（§5.5） | なし |
| `ProgressSummary` | SC-01、SC-03 | 概念ごとの学習状況 | なし |
| `ReadMarker` | SC-02a | 「読み終えた」 | なし |
| `CompareView` | SC-02b | 設計の選択、ファイルの選択、差分の表示 | 左右の設計、選んでいるファイル、表示形式 |
| `ChangeSimulator` | SC-02c | 変更要求の選択、2つの設計の差分と修正量 | 選んでいる変更要求、2つの設計、枠ごとのファイル |
| `Quiz` | SC-02d | 出題・判定・結果のまとめ・解き直し。選択肢の並べ替え（FR-055、Could）を作る場合は、表示のたびに乱数で順番を決める | 何問目か、解答、解き直しかどうか、選択肢の順番 |

- エディタ（CodeMirror）は、`ExerciseEditor` が表示されるときにだけ読み込む（NFR-05）。
- 部品の状態（選んでいる設計など）は保存しない。保存するのは §6 の学習データだけ。
- `CompareView` と `ChangeSimulator` で最初に表示するファイルは、変更行数が最も多いファイルとする。同じ数のときは、相対パスの文字コード順で先のものとする。
- FR-068（自分のコードと模範解答の差分、Could）を作る場合は、`build/diff.ts` の行差分の部分を `src/domain` に移し、ビルドとブラウザで共用する。

### 5.4 表示言語の決定とちらつき防止

1. 生成する HTML には、最初から `<html data-lang="java">` を書いておく（JavaScript が動かないときは Java で表示される。DES-01 §7）。
2. `<head>` の先頭にある小さなスクリプトが、localStorage から表示言語を読み取り専用で読み、`data-lang` を書き換える。読めない場合（保存領域が使えない、JSON が壊れている、版が新しい、`languages.yaml` にない言語 ID）は Java のままにする。このスクリプトは、学習データストアの定数からビルド時に生成する（§2.1）。
3. CSS は、表示言語に従う領域（`data-follow-lang` を付けた要素）の中で、`data-lang` と違う言語の表示を隠す。そのため、描画の前に正しい言語が決まる。模範解答とエディタは表示言語に一律には従わないため（DES-01 §3.10）、この仕組みの対象にせず、`ExerciseEditor` が自分で出し分ける。
4. このスクリプトのハッシュ値をビルド時に計算し、Astro の CSP の機能（`security.csp.scriptDirective.hashes`）に渡す。Astro が書き出すスクリプトのハッシュ値は、Astro が自動で入れる（§9.3、T9 の結果）。
5. 表示言語を切り替えると、`LanguageSwitcher` が `LearningStore` に保存し、`data-lang` を書き換える。対話部品は `LearningStore` の通知で表示を更新する（ファイルの選び直しは DES-01 §6.3 と §5.3）。

### 5.5 画面に出すメッセージ

| 場面 | 文言 |
| --- | --- |
| localStorage が使えない | 学習の記録を保存できません（ブラウザの設定やプライベートモードの可能性があります）。このページを表示している間だけ記録します。 |
| 容量不足 | 保存できる容量を超えたため、記録できませんでした。「学習データ」の画面で、不要な記録を消してください。 |
| 記録が壊れていた | 学習の記録が読み込めなかったため、初期化しました。元の内容は「学習データ」の画面から書き出せます。 |
| 新しい版の記録 | 新しい版のアプリで保存された記録があります。ページを再読み込みしてください。 |
| 読み込みの失敗 | ファイルの形式が正しくないため、読み込めませんでした（理由）。今の記録はそのままです。 |
| 全消去の確認 | 学習の記録をすべて消します。元に戻せません。よろしいですか。 |
| JavaScript が動かない | この操作には JavaScript が必要です。ブラウザの設定で JavaScript を有効にしてください。 |
| 下書きが上限に達した | 下書きは1つの言語につき20,000文字までです。 |
| 正解データを取得できない | 判定できませんでした。通信状態を確かめて、もう一度解答してください。 |
| 実装課題の注意（FR-069） | あなたのコードは実行・採点されず、このブラウザの外にも送られません。評価は自己評価です。 |

### 5.6 実装課題のエディタと下書き

開始コードと模範解答は、複数のファイルからなる。エディタはこれを1つのテキストとして扱い、ファイルの区切りをコメント行で示す（K33）。

```java
// ===== Main.java =====
public class Main {
    …
}
// ===== Transmission.java =====
class Transmission {
    …
}
```

- 区切り行の書き方は言語ごとに決める。Java と C++ は `// ===== ファイル名 =====`、VBA は `' ===== モジュール名（クラス／標準） =====`。
- 新しいクラスを足すときは、学習者が区切り行を書き足してから、その下に書く。コードは実行も解析もしないため、区切り行が崩れても動作に影響はない。
- 模範解答は、ファイルごとのタブで色付けして表示する（区切り行は使わない）。
- 下書きは、言語ごとに1つの文字列として保存する（§6.2）。上限は1つの言語につき20,000文字とし、エディタはそれ以上の入力を受け付けず、§5.5 の文言を出す。
- 自動保存は、入力が止まってから1秒後、エディタから離れたとき、ページを離れるときに行う（入力のたびに保存すると、学習データ全体の読み書きが多くなるため）。

## 6. 学習データ

### 6.1 保存場所

| キー | 内容 |
| --- | --- |
| `oop-lab.learning-data` | 学習データ（§6.2） |
| `oop-lab.learning-data.broken` | 壊れていた学習データの退避先。最新の1件だけを残す（K28） |

### 6.2 形式（版 1）

```json
{
  "schemaVersion": 1,
  "updatedAt": "2026-10-16T12:00:00.000Z",
  "settings": { "displayLanguage": "java" },
  "explanations": {
    "encapsulation": { "readAt": "2026-10-16T12:00:00.000Z" }
  },
  "quiz": {
    "encapsulation.q01": { "correct": true, "answeredAt": "2026-10-16T12:00:00.000Z" }
  },
  "exercises": {
    "encapsulation.ex01": {
      "implementationLanguage": "java",
      "drafts": {
        "java": { "code": "…", "savedAt": "2026-10-16T12:00:00.000Z" }
      },
      "evaluations": {
        "self": {
          "results": { "encapsulation.ex01.c1": true, "encapsulation.ex01.c2": false },
          "evaluatedAt": "2026-10-16T12:00:00.000Z"
        }
      }
    }
  }
}
```

| 項目 | 内容 |
| --- | --- |
| `schemaVersion` | 形式の版（NFR-15 ②） |
| `settings.displayLanguage` | 表示言語の ID |
| `explanations` | 概念 ID ごとの「読み終えた」日時 |
| `quiz` | 設問 ID ごとの最新の正誤と日時 |
| `exercises.*.implementationLanguage` | 課題ごとに選んだ実装言語（言語 ID か `other`） |
| `exercises.*.drafts` | 実装言語ごとの下書き（ファイルの区切り行を含む1つの文字列。§5.6）。1つの言語につき20,000文字まで |
| `exercises.*.evaluations` | 評価方法ごとの結果。初回は `self`（自己評価）だけ。将来の採点は別の評価方法として並べる（NFR-15 ④）。知らない評価方法の記録は、消さずに残す |

削除された概念・設問・課題の記録は、データには残したまま、表示と集計では無視する（NFR-11）。

### 6.3 書き込みの手順

1. localStorage から最新の学習データを読み直す。
2. 解析して検証する（失敗したときは §6.4）。
3. 呼び出し側から渡された変更を加える。
4. `updatedAt` を更新し、JSON にして書き込む。容量不足のときは、書き込まずに `quota-exceeded` を返す。
5. 購読している部品に通知する。

他のタブで変更されたときは、ブラウザの `storage` イベントで知り、読み直して購読者に通知する。

**状態ごとの振る舞い**

| `status` | `get` が返すもの | `update` の振る舞い |
| --- | --- | --- |
| `ok` | 最新の学習データ | 上の手順で保存する。容量不足のときは保存せず `quota-exceeded` を返す。画面の部品は、入力中の内容（書きかけのコードなど）を捨てずに持ち続ける |
| `unavailable` | メモリ上の学習データ | localStorage には書かず、メモリ上の学習データに変更を加えて `{ ok: false, reason: "unavailable" }` を返す。帯は最初の1回だけ出す |
| `newer-version` | メモリ上の学習データ（初期データから始める） | 同上（理由は `newer-version`） |

### 6.4 読み込み時の判定

| 状況 | 振る舞い | `status` |
| --- | --- | --- |
| キーがない | 初期データを使う | `ok` |
| 版が同じ | そのまま使う | `ok` |
| 版が古い | 新しい形式に移行して保存する | `ok` |
| 版が新しい | 読み込まず、保存もしない。そのページの間だけメモリ上で記録する | `newer-version` |
| 全体が JSON として読めない、または `schemaVersion` がない | 退避先に元の文字列を保存してから初期化する。帯で知らせる | `ok` |
| localStorage が例外を出す | そのページの間だけメモリ上で記録する | `unavailable` |

**検証の規則**

- 検証するのは形（項目の型と、必須の項目があること）だけとする。ID や言語 ID が教材にあるかどうかは検証しない。教材から消えた記録や、将来減らした言語の記録のために、学習データ全体が初期化されないようにするためである（NFR-11）。
- 一部の項目だけ形が違うときは、その項目だけを捨てて残りを使う（例: ある設問の記録だけが壊れていれば、その記録だけを捨てる）。20,000文字を超える下書きも、その下書きだけを捨てる。
- `settings.displayLanguage` が `languages.yaml` にない言語のときは、Java として扱う（記録は書き換えない）。

**版の移行の手順**

1. 版 n から n+1 への移行関数を、版ごとに1つ用意する（初回は版1だけなので、移行関数はない）。
2. 読み込んだ版から現在の版まで、移行関数を順に当てる。
3. 移行の後に検証する。
4. 移行または検証に失敗したら、元の文字列を退避して初期化する。
5. 成功したら、すぐに保存する。

### 6.5 書き出し・読み込み（FR-073・Could）

- 書き出し: 学習データの JSON に `"format": "oop-lab-learning-data"` を加えて、ファイルとして保存させる。

## 7. VBA 確認ツール

### 7.1 構成

| ファイル | 役割 |
| --- | --- |
| `tools/vba-verify/Invoke-VbaVerify.ps1` | 入口。`-Concept` で概念を絞れる |
| `tools/vba-verify/VbaVerify.psm1` | 対象の列挙・写しの加工・Excel の操作・記録 |
| `tools/vba-verify/templates/VerifyCapture.bas` | 出力を集める標準モジュール |
| `tools/vba-verify/templates/VerifyRunner.bas` | 実行の入口を呼び、出力またはエラーを返す標準モジュール |

Windows PowerShell 5.1 で動くように作る（ユーザの PC に標準で入っているため）。PowerShell のファイルは UTF-8（BOM 付き）で保存する。Windows PowerShell 5.1 は、BOM のない UTF-8 のファイルを Shift_JIS として読むためである（T2 の試作で判明）。

### 7.2 確認の対象

| 対象 | 確認の種類 | 期待結果 |
| --- | --- | --- |
| `variations/*/vba` | 実行 | 概念の `expected-output.txt` |
| `changes/*/*/vba` | 実行 | 変更要求の `expected-output.txt` |
| `exercises/*/answer/vba` | 実行 | その課題の `expected-output.txt` |
| コード読解の設問の VBA のコード | コンパイル | なし（DQ2） |

### 7.3 写しの加工

確認の対象を一時フォルダに写し、写しの中でだけ次の加工をする。

| 加工 | 内容 |
| --- | --- |
| `Debug.Print` の置き換え | 行頭（字下げは可）の `Debug.Print 式` を `VerifyCapture.WriteLine (式)` に、`Debug.Print` だけの行を `VerifyCapture.WriteLine ""` に置き換える |
| 文字コード | UTF-8 から Shift_JIS（CP932）に変える。CP932 で表せない文字があれば、その状態を失敗にする |
| 改行 | CRLF に変える |
| 見出し行 | `.cls` には次の9行を付ける: `VERSION 1.0 CLASS` ／ `BEGIN` ／ `  MultiUse = -1  'True` ／ `END` ／ `Attribute VB_Name = "名前"` ／ `Attribute VB_GlobalNameSpace = False` ／ `Attribute VB_Creatable = False` ／ `Attribute VB_PredeclaredId = False` ／ `Attribute VB_Exposed = False`。`.bas` には `Attribute VB_Name = "名前"` の1行を付ける |
| 確認用モジュール | `VerifyCapture.bas` と `VerifyRunner.bas` を加える。`VerifyRunner.RunMain` は、エラー処理の中で `Program.Main` を呼び、集めた出力（エラー時は「ERROR: 番号 説明」）を文字列で返す |

### 7.4 実行の手順

1. レジストリ `HKCU\Software\Microsoft\Office\16.0\Excel\Security\AccessVBOM` の値を読む。1 なら「確認前から有効でした」と表示する。そのうえで 1 にする。
2. Excel を非表示・警告なしで起動する。
3. 状態ごとに新しいブックを作り、写しを取り込む。
4. コンパイルの確認（すべての状態）: VBE の「VBAProject のコンパイル」（コントロール ID 578）を実行する。実行後にそのメニューが無効になっていれば成功とする。コンパイルエラーがあるとメニューは有効のまま残り、ダイアログは出ない（T2 の結果）。
5. 実行の確認（設計・変更後・模範解答）: コンパイルに成功したときだけ、`Application.Run("'ブック名'!VerifyRunner.RunMain")` を呼ぶ。戻り値と期待結果を比べ（改行を LF にそろえて比べる）、ブックを保存せずに閉じる。コンパイルエラーのあるまま実行すると Excel が異常終了するため、コンパイルに失敗した状態は実行しない（T2 の結果）。
6. 時間切れ: 念のため、1つの操作につき30秒を超えたら、Excel を強制終了してその状態を失敗にし、Excel を起動し直して続ける（終わらない処理などに備える）。
7. 終了時（失敗時を含む）: Excel を終了して COM を解放し、レジストリの値を 0 に戻し、一時フォルダを消す。
8. 結果を画面に一覧表示し、確認記録（§7.5）を書き出す。

### 7.5 確認記録 `verification/vba.json`

```json
{
  "tool": "vba-verify",
  "toolVersion": 1,
  "excelVersion": "16.0.xxxxx",
  "verifiedAt": "2026-10-16T12:00:00Z",
  "entries": [
    {
      "target": "content/concepts/encapsulation/variations/proper/vba",
      "kind": "run",
      "expected": "content/concepts/encapsulation/expected-output.txt",
      "hash": "sha256:…",
      "result": "passed"
    },
    {
      "target": "content/concepts/encapsulation/quiz/questions.yaml#encapsulation.q09",
      "kind": "compile",
      "hash": "sha256:…",
      "result": "passed"
    }
  ]
}
```

**ハッシュ値の計算方法**（PowerShell と Node.js で同じ値になるように定める）

1. 対象のファイル（ソース一式と期待結果のファイル）を、リポジトリのルートからの相対パス（`/` 区切り）で並べる。並べ方は文字コードの値の順（大文字と小文字を区別する順。.NET の `Ordinal` 比較、JavaScript の既定の並べ替えと同じ）とする。
2. 各ファイルをバイト列として読み、UTF-8 として扱い、改行を LF にそろえてから内容の SHA-256 を計算する。そして「相対パス＋改行＋内容の SHA-256（16進の小文字）＋改行」を作り、すべてつなげる。
3. つなげた文字列（UTF-8）の SHA-256 を `sha256:` に続けて書く。
4. 設問のコードは、`moduleName`・`moduleType`・本文（改行を LF にそろえたもの）を改行でつないだ文字列の SHA-256 とする。

### 7.6 CI での照合（`check-vba-record.ts`）

教材から VBA の確認対象をすべて列挙する。それぞれについて、ハッシュ値が一致し、結果が `passed` の記録があることを確かめる。足りなければ、対象の一覧を出して失敗する。

### 9.2 デプロイ

- Cloudflare Workers の静的アセット配信として、`wrangler` でデプロイする。本番は `deploy`、プレビューはバージョンを作ってプレビュー URL を得る。プレビュー URL は Pull Request にコメントで書く。
- プレビューは、Wrangler の設定で `preview_urls: true` とし、`wrangler versions upload --preview-alias pr-<番号>` で Pull Request ごとの URL を作る。プレビュー URL は誰でも見られる（K37 と同じ扱い）。静的アセットだけの Worker で使えることは、M1 の最初のデプロイで確かめる（§12 T1）。
- シークレット: `CLOUDFLARE_API_TOKEN`（Workers の編集だけを許可したトークン）、`CLOUDFLARE_ACCOUNT_ID`。

### 9.3 配信時のヘッダ（`public/_headers`）

| ヘッダ | 値 |
| --- | --- |
| `Content-Security-Policy` | `frame-ancestors 'none'`（ページ内の meta 要素では指定できない項目だけを、ヘッダで送る。残りは下の「ページごとの CSP」） |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=()` |

`style-src` に `'unsafe-inline'` を入れるのは、コードの色付けや画面部品が `style` 属性を使うためである。スクリプトの実行は許さないので、危険は小さい。

**ページごとの CSP（Astro の CSP の機能。T9 の結果）**

Astro の `security.csp` を使い、ページごとに `<meta http-equiv="content-security-policy">` を出力させる。Astro が対話部品を読み込むために書き出すスクリプトのハッシュ値は Astro が自動で入れ、表示言語を決める先頭スクリプト（§5.4）のハッシュ値は設定で渡す。

| 項目 | 値 |
| --- | --- |
| `script-src` | `'self'` と、ページ内のスクリプトのハッシュ値 |
| `style-src` | `'self' 'unsafe-inline'`（`'unsafe-inline'` があると、Astro はスタイルのハッシュ値を出さない） |
| その他（`security.csp.directives` で指定） | `default-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'self'; form-action 'none'` |

ヘッダとページの両方に CSP があると、ブラウザは両方を満たすものだけを許す。そのため、ヘッダの CSP には `default-src` や `script-src` を書かない（書くと、ページ内のスクリプトがヘッダ側の規則で止められる）。

ビルドでは、小さなファイル（日本語フォントの一部の分割ファイルなど）を CSS に data: URI として埋め込ませない（`vite.build.assetsInlineLimit: 0`）。埋め込むと `font-src 'self'` に止められるためである（M1 の E2E テストで判明）。
